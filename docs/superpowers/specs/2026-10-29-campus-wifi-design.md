# 교내 와이파이 연결 도우미 — 1차 기획서

작성일: 2026-10-29 · 개정: 2026-10-31  
상태: 2026-10-29 사용자 승인으로 개발 시작. BASE와 실제 연결 성공 시 해금 기준 유지. 2026-10-31 계정 연결, 세 로그인 모두 첫 출시 조건, 그림 없는 AP 숨김을 결정했다. 2026-11-01 물리 AP 단위 캐릭터, 직접 설치 파일 배포, Windows 현장 시험을 결정했다. 현재 범위와 진행은 [기획 총괄표](../../product/project-planning.md)가 기준이다.

## 1. 만들려는 서비스

광주소프트웨어마이스터고등학교(GSM)에서만 사용하는 프로그램이다. 학교는 한 곳으로 고정하며 학교 선택·추가·여러 학교 운영은 개발 범위와 후속 확장 계획에서 제외한다.

학생이 와이파이마다 비밀번호를 직접 입력하고, 연결 상태가 나빠질 때 다른 와이파이를 직접 고르는 부담을 줄인다. 관리자는 웹에서 학교 네트워크와 정확한 비밀번호를 등록한다. Android·Windows 앱은 해당 정보를 동기화하고 주변에서 발견한 학교 네트워크를 비교해 연결을 지원한다.

핵심 사용 방식은 처음 로그인·권한 설정 후 자동 관리를 켜두면, 사용자가 다른 작업을 하거나 앱 화면을 내려도 연결 관리가 운영체제에서 허용하는 범위 안에서 이어지는 것이다. 매번 앱을 다시 열어 검사·연결 버튼을 누르는 작업을 일상적인 사용 흐름으로 요구하지 않는다.

지원 대상은 Android 휴대폰과 Windows 노트북이다. 관리자는 서비스 운영자인 사용자 한 명이다. 관리자 웹과 두 앱은 공통 서버를 이용한다.

성공의 기준은 등록된 학교 네트워크의 비밀번호를 학생이 직접 입력하지 않아도 되는 것, 불필요한 수동 네트워크 선택을 줄이는 것, 전환이 실제로 도움이 됐는지 기록으로 확인할 수 있는 것이다. 초기 권한·네트워크 등록에 필요한 운영체제의 동의 화면은 제공한다.

## 2. 확정한 조건과 설계 제안

### 사용자와 확정한 조건

- 광주소프트웨어마이스터고등학교 전용으로 개발한다.
- 관리자 화면은 웹으로 만든다.
- Android 앱은 Kotlin으로 만든다.
- Windows 앱은 C#으로 만든다.
- 관리자 권한은 운영자 한 명에게만 부여한다.
- 일반 사용자에게는 세 가지 로그인 경로를 제공한다.
  1. 학생 학교 이메일 소유를 인증해 로그인한다.
  2. 관리자가 개인별로 발급한 초대코드만 입력해 로그인한다. 이 경로에는 이메일이나 별도의 비밀번호를 요구하지 않는다.
  3. 학교에서 사용하는 DataGSM 계정으로 OAuth 로그인한다. 공식 문서에서 외부 서비스 연동 지원을 확인했다.
- 학생 이메일은 로컬 부분이 s로 시작하고 도메인이 gsm.hs.kr인 주소다. s 다음의 번호·문자 규칙은 아직 주어지지 않았다.
- 초대코드는 공용 코드가 아니라 한 사람에게 하나씩 발급한다.
- 사용자가 자동 관리를 활성화하면 앱 화면을 계속 열어두지 않아도 주변 학교 와이파이 확인·품질 판단·연결 관리를 자동으로 수행하는 사용 방식을 목표로 한다. Android의 실제 동작 범위는 OS 제한과 실기기 검증 결과를 따른다.
- 와이파이 도감은 사용자에게 수집하는 즐거움을 주는 게임 요소다. 각 와이파이에 재미있는 이름과 캐릭터 그림을 붙이고, 미발견 캐릭터는 회색으로 표시한다.
- Android·Windows 사용자 도감은 캐릭터 이미지를 모아 보는 화면이다. 지도·도면·AP 설치 위치 조회와 편집은 관리자 웹 전용이며 사용자 도감에는 넣지 않는다.
- 도감은 등록된 학교 와이파이에 실제로 연결 성공해야 해금한다. 주변에서 신호를 발견한 것만으로 해금하지 않는다.
- 관리자 웹에서 등록된 각 와이파이의 설치 위치를 모두 확인할 수 있게 한다. 현재 주변에 보이는 AP만 표시하는 목록으로 제한하지 않는다.
- 디자인 시스템은 사용자가 제공한 BASE 참고 자료를 기반으로 한다. 적용 기준은 ../../design/design-system.md에 정리한다. 화면의 세부 디자인은 제품 개발과 함께 진행한다.
- 모든 주변 네트워크의 속도를 계속 측정하지 않는다. 신호와 최근 기록으로 후보를 좁히고 필요할 때 품질을 확인한다.
- 2026-10-29 사용자가 기획 검토 후 개발 시작을 승인했다. 제품 이름은 와글(waggle), GitHub 공개 저장소와 PR 작업 흐름을 사용한다. 관리자 웹에 프로젝트 문서 메뉴를 포함한다.

### 기획 작성자가 제안하는 기본값

다음 항목은 사용자 확정 요구와 구분되는 설계 제안이다.

- 관리자 웹과 공통 서버의 주 언어는 TypeScript로 한다. 구체 프레임워크·호스팅·메일 제공업체는 구현 계획에서 정한다.
- 영속 데이터는 관계형 데이터베이스에 저장한다. 구체 제품·배포 방식은 구현 계획에서 정한다.
- 학교 이메일 로그인은 이메일로 보낸 일회용 인증번호를 입력하는 방식으로 한다. 계정 비밀번호는 추가하지 않는다.
- 개인 초대코드의 소유자는 같은 코드로 자신의 휴대폰과 노트북을 모두 로그인할 수 있다. 한 기기에서 소비되는 일회용 초대권으로 만들지 않는다.
- 세 로그인 경로의 일반 사용자 권한은 동일하다. 초대코드나 DataGSM의 역할 값만으로 이 서비스의 관리자 권한을 얻을 수 없다.
- DataGSM은 Authorization Code + PKCE 방식으로 연동한다. 로그인 화면에서는 이를 기본 진입점으로 제안하되 이메일·개인 코드 경로도 제공한다.
- Windows의 자동 연결·전환 동작을 먼저 검증하고, Android 지원 범위를 실제 기기에서 검증한 뒤 사용자 앱 범위를 확정한다.
- 공유 비밀번호 방식의 네트워크를 초기 대상으로 한다. 실제 학교가 다른 인증 방식을 사용한다면 현장 검증 단계에서 설계를 갱신한다.

## 3. 검토한 접근과 선택

| 접근                                     | 장점                                             | 비용·제약                                                              | 결정                              |
| ---------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------- | --------------------------------- |
| 기기별로 학생이 직접 와이파이를 등록     | 서버 구성이 작음                                 | 비밀번호 입력 부담이 학생마다 반복됨                                   | 중앙 등록 요구에 맞지 않아 제외   |
| 공통 서버 + 관리자 웹 + OS별 네이티브 앱 | 중앙에서 정보를 관리하고 OS별 연결 API 사용 가능 | 웹·서버와 두 앱을 각각 관리해야 함                                     | 사용자가 선택한 웹·Kotlin·C# 구성 |

사용자 인증은 학교 이메일, 개인 초대코드, 학교 통합 인증인 DataGSM을 검토했다. 최종 요구는 세 경로를 함께 제공하는 것이다. DataGSM 계정으로 로그인하거나, 학교 이메일을 인증하거나, 운영자가 발급한 개인 코드로 사용할 수 있다. DataGSM을 기본 진입점으로 제안하는 이유는 학교가 이미 사용하는 계정으로 인증할 수 있고 공식 OAuth 연동 문서가 있기 때문이다.

## 4. 계정과 로그인

### 관리자

- 최초 설정 과정에서 지정한 관리자 계정 한 개만 운영한다.
- 공개 회원가입에서 관리자 역할을 고르는 기능은 제공하지 않는다.
- 학생 이메일 형식에 맞는다는 이유로 관리자 권한을 주지 않는다.
- DataGSM 사용자 정보의 role이 ADMIN이어도 이 서비스의 관리자로 자동 승격하지 않는다. 이 서비스에서 사전 지정한 운영자 한 명만 관리자로 취급한다.
- 관리자 웹은 네트워크·접속정보 관리, 개인 초대코드 발급·회수, 사용자와 세션 관리를 제공한다.
- 관리자 인증 수단과 복구 수단은 배포 전에 확정한다. 관리자가 이미 사용하는 신뢰할 수 있는 인증 제공자를 연결하는 방식도 구현 계획에서 선택할 수 있다.
- 모든 관리 API에서 서버가 관리자 권한을 확인한다.

### 학교 이메일 사용자

- 이메일을 파싱한 뒤 도메인이 정확히 gsm.hs.kr인지 확인한다. 다른 도메인이나 하위 도메인을 자동으로 허용하지 않는다.
- 로컬 부분은 s로 시작하는지 확인한다. 대소문자 비교 방식은 구현 세부사항으로 정하고, 별도의 학번 규칙을 추측해 추가하지 않는다.
- 주소 모양 검사만으로 로그인시키지 않는다. 해당 주소로 보낸 일회용 인증번호를 확인한 뒤 계정을 만들거나 기존 계정으로 로그인한다.
- 인증번호는 짧은 유효기간과 재시도·재발급 제한을 둔다. 구체 수치는 구현 계획에서 정한다.
- 인증번호·비밀번호·초대코드는 로그나 분석 이벤트에 남기지 않는다.

### 개인 초대코드 사용자

- 관리자가 발급 대상별로 충분히 추측하기 어려운 코드를 생성한다. 운영자는 대상을 구분할 별칭을 붙일 수 있다.
- 일반 사용자는 코드만 입력해 로그인한다. 이메일 입력·학교 이메일 인증·별도 계정 비밀번호를 요구하지 않는다.
- 발급 시 코드와 일반 사용자 내부 계정을 연결한다. 코드로 로그인할 때마다 새 사용자를 만들지 않는다.
- 코드 소유자의 휴대폰·노트북에는 각각 독립된 기기 세션을 발급한다.
- 코드는 개인에게 발급하지만 코드 소지만으로 로그인하는 자격증명이다. 앱이 실제 사람의 신원을 추가로 증명하는 것은 아니다.
- 관리자가 코드를 회수하거나 재발급할 수 있다. 회수 시 연결된 갱신 세션을 무효화하고 이후 로그인·정보 갱신을 막는다.
- 코드는 발급할 때만 전체 값을 보여준다. 저장소에는 검증용 다이제스트를 보관하고, 분실 시 새 코드를 발급한다.
- 이메일·개인 코드·DataGSM 계정을 이름이나 이메일 일치만으로 자동 병합하지 않는다.
- 2026-10-31 결정: 기존 로그인 상태에서 다른 인증 수단을 그 자리에서 새로 인증해 같은 계정에 연결하는 기능을 첫 버전에 포함한다. 한 계정에는 수단별로 한 개만 연결한다. 이미 다른 계정에 묶인 수단이면 사용자 확인 후 수집 집합을 합집합으로 합치고 상대 계정의 기기 세션을 회수한다. 마지막 수단은 해제할 수 없다. 연결하지 않으면 경로별 계정이 따로 생길 수 있음을 로그인 안내에 반영한다.

### DataGSM 사용자

- 공식 문서 확인일은 2026-10-29다. 문서상 OAuth 2.0 Authorization Code Grant와 PKCE를 지원하며, 외부 서비스용 클라이언트를 등록할 수 있다.
- 사용자는 앱에서 DataGSM 로그인을 선택하고 외부 브라우저에서 DataGSM 인증·동의를 진행한다. 우리 앱이나 서버가 학교 계정의 비밀번호를 직접 입력받지 않는다.
- 사전에 DataGSM 클라이언트 관리 페이지에서 이 서비스의 클라이언트를 생성하고 허용할 리다이렉트 URI를 등록한다. 이번 기획 단계에서는 클라이언트 생성이나 실제 사용자 로그인을 수행하지 않았다.
- 인증 시 PKCE S256과 일회성 state를 사용하고 인증 요청·콜백을 같은 로그인 시도에 연결한다. client_secret이 필요한 구성이라면 서버에서만 보관한다.
- 구현의 기본 방향은 공통 서버의 HTTPS 콜백에서 인증 코드를 교환하고 인증된 사용자 정보를 확인한 다음, 이 서비스의 기기 세션을 발급하는 것이다. Android·Windows 앱의 복귀는 원래 로그인한 기기에 묶인 단기 일회용 교환 수단으로 처리한다. DataGSM 토큰이나 장기 서비스 토큰을 앱 복귀 URL에 넣지 않는다.
- Android 외부 브라우저·App Link, Windows 외부 브라우저·복귀 경로 등 세부 방식은 클라이언트 등록 조건을 확인한 뒤 구현 계획에서 정한다. 네이티브 앱에 공통 비밀키를 내장하지 않는다.
- DataGSM 사용자 데이터 조회 API를 서버에서 호출해 공급자 사용자 ID와 계정 상태를 확인한다. 앱이 보낸 검증되지 않은 프로필·토큰 내용만으로 로그인시키지 않는다.
- 기본 조회 권한은 datagsm:self_read로 필요한 최소 범위만 등록·요청한다. 이 권한의 응답에 추가 학생 정보가 포함돼도 로그인에 불필요한 학급·기숙사 등의 데이터를 보관하지 않는다.
- 내부 계정은 공급자 이름 DataGSM과 공급자의 사용자 고유 ID 조합으로 연결한다. 이메일은 계정의 고유 식별자로 대신 사용하지 않는다.
- 학생 대상 서비스라는 목적에 따라 활성 재학생 계정만 일반 사용자 자동 가입 대상으로 삼는 것을 기본값으로 제안한다. 신규 연동은 objectType을 사용한다. isStudent는 공식 문서에서 deprecated로 표시된 파생값이다. status가 ACTIVE이고 objectType이 STUDENT여도 student.role이 GRADUATE 또는 WITHDRAWN이면 재학생으로 취급하지 않는다. student.isLeaveSchool도 함께 확인하고, 누락·충돌하는 상태는 자동 허용하지 않는다. 선생님·미연결 계정은 개인 초대코드 경로를 사용할 수 있다.
- 이 경로에는 이메일 직접 로그인 전용 규칙인 s 접두어만으로 다시 자격을 판정하는 로직을 적용하지 않는다. DataGSM이 제공하는 인증된 학생 정보를 기준으로 한다.
- DataGSM 인증 취소·실패·제공자 장애는 로그인 오류로 표시하고 다른 두 로그인 경로를 안내한다. 기존에 유효한 이 서비스의 로그인 세션과 저장된 와이파이 연결을 즉시 끊지 않는다.
- DataGSM 인증만 추가하면 와이파이가 연결되는 것은 아니다. 성공 후 기존과 동일하게 이 서비스의 권한 검사·학교 설정 배포·OS 연결 절차를 수행한다.

### 세션과 학교 정보 접근

- 세 경로 모두 로그인 결과로 이 서비스의 기기별 세션을 발급한다. DataGSM 토큰 자체를 이 서비스의 API 세션으로 대신 사용하지 않는다.
- 짧은 액세스 세션과 회수 가능한 갱신 수단을 사용한다. 정확한 만료 시간은 구현 계획에서 정한다.
- 앱의 운영체제 보안 저장소에 세션과 필요한 로컬 정보를 보관한다.
- 일반 사용자도 관리자 쓰기 API를 호출할 수 없다.
- 코드·계정 회수는 서비스의 API 접근과 세션 갱신 차단에 적용한다. 이미 운영체제에 저장된 학교 비밀번호를 원격으로 모두 무효화한다고 약속하지 않는다. 학교 와이파이 자체의 접근 차단에는 네트워크 측 자격증명 관리가 필요하다.

## 5. 네트워크 등록과 배포

관리자가 접속정보를 등록하는 기본 단위는 학교 네트워크 설정이다. 실제 설치 장소는 AP별 항목으로 별도 관리한다.

- 표시 이름
- SSID와 보안 방식
- 해당 네트워크의 정확한 비밀번호 또는 지원하는 인증 정보
- 선택적인 건물·층 등 설명
- 사용 여부와 설정 버전
- 선택적인 AP 식별 정보와 메모

비밀번호 후보 7개를 매번 순서대로 시험하는 것을 주 흐름으로 삼지 않는다. 관리자가 알고 있는 정확한 네트워크·비밀번호 조합을 입력하고 앱은 그 조합을 사용한다.

같은 SSID 아래 AP가 여러 개인 경우에는 네트워크의 연결 정보와 AP별 관찰 기록을 구분한다. AP 관찰 기록은 BSSID 등으로 구분하며, 하나의 물리 장치가 여러 BSSID를 가질 수 있음을 전제로 한다. AP를 하나씩 비밀번호 중복 등록하도록 요구하지 않는다.

### 관리자에서 모든 와이파이 위치 보기

- 관리자에게 등록된 전체 AP 목록과 위치 조회 화면을 제공한다. 등록한 AP는 현재 학생 기기 주변에 없더라도 조회할 수 있다.
- AP별 네트워크·BSSID, 관리용 이름, 건물, 층, 구체적인 설치 장소를 관리한다. 지도나 도면을 도입할 경우 해당 도면과 표시 좌표를 연결한다.
- 건물·층별로 목록을 좁히고, 지도 표시와 목록 선택을 연결하는 UI를 제안한다. 위치가 없는 AP도 전체 목록에 남기고 위치 미등록으로 명시한다.
- 위치는 관리자가 실제 설치 장소를 확인해 등록한다. 네트워크 이름·학생 학급·기숙사 정보만으로 AP 위치를 자동 확정하지 않는다.
- 설치 위치와 실시간 사용 가능 여부를 구분한다. 최근 관찰 기록이 있으면 관찰 시각을 표시하고, 오래 보이지 않았다는 이유만으로 고장·오프라인으로 확정하지 않는다.
- 실제 학교의 배치도·층별 도면은 아직 없다. 초기 화면 시안의 건물 배치, AP 식별자와 위치는 예시 데이터이며 운영용 등록 자료로 사용하지 않는다.

관리자는 목록을 추가·수정·비활성화한다. 서버는 승인된 일반 사용자 앱에 필요한 설정과 버전을 전송한다. 앱은 처음 로그인할 때와 이후 동기화 시 변경을 적용하고 결과를 표시한다. 비밀번호를 화면·서버 로그·공개 통계에 노출하지 않는다.

앱이 연결할 때는 접속정보를 사용할 수 있어야 한다. 따라서 학교 비밀번호는 서버에서 복호화 가능한 암호화 저장이 필요하며, 로그인 비밀번호처럼 단방향 해시만 저장하는 방식으로 대체하지 않는다. 복호화 키는 데이터베이스와 분리해 관리한다. 전송에는 TLS를 사용한다.

## 6. 사용자 앱의 연결 흐름

1. 로그인한 뒤 필요한 권한과 네트워크 등록 동의를 안내한다.
2. 승인된 학교 네트워크 설정을 동기화하고 로컬에 보관한다.
3. 현재 연결과 최근 주변 검색 결과를 확인한다.
4. 등록된 학교 네트워크와 일치하는 주변 후보만 비교한다.
5. 현재 연결이 충분하면 유지한다.
6. 상태가 지속적으로 나쁘고 개선 가능성이 큰 후보가 있으면 플랫폼이 허용하는 방식으로 연결을 요청하거나 OS에 후보를 제공한다.
7. 연결 성공·실패와 현재 사용 가능 여부를 확인한다.
8. 실패하면 가능한 범위에서 마지막으로 사용 가능했던 후보로 복구를 시도하고, 복구가 어려우면 상태와 수동 조치 방법을 표시한다.

앱에는 현재 연결, 신호 상태, 후보와 선택 이유, 마지막 동기화, 연결 실패 원인, 자동 관리 켜기·끄기, 수동 새로고침을 제공한다. OS 권한이 없거나 검색 결과가 오래된 경우에는 상태를 분명히 표시한다.

### 화면을 내려도 이어지는 자동 관리

- 초기 로그인·필수 권한·네트워크 등록 동의가 끝나면 사용자는 자동 관리 시작을 한 번 선택한다. 이후 현재 연결 확인, 허용된 주변 검색 결과 처리, 후보 비교, 연결 요청과 실패 처리를 자동으로 수행한다.
- 관리 상태와 연결 판단 엔진을 화면의 수명과 분리한다. 화면을 다시 열었다고 관리 엔진을 중복으로 시작하거나 로그인·설정 다운로드를 매번 반복하지 않는다.
- 일상적인 후보 확인과 전환마다 앱 창·확인 팝업을 띄우지 않는다. 운영체제 필수 동의나 권한 복구 등 사용자 행동이 필요한 경우만 안내한다.
- 관리 중, 학교 네트워크 없음, 재연결 중, 권한 필요, 일시 중지, 중단됨을 구분해 실제 상태를 표시한다. 관리 프로세스가 정지했는데 실행 중으로 계속 표시하지 않는다.
- Windows는 기본 창을 닫으면 트레이로 보내 관리 프로세스를 유지하는 구성을 제안한다. 트레이에서 상태 확인·일시 중지·완전 종료를 제공하고, 최초 사용 시 창 닫기의 의미를 안내한다.
- Android는 사용자가 앱을 보고 있을 때 자동 관리를 시작한다. 목적에 맞는 foreground service 사용이 가능한지 검증하고, 사용하는 경우 OS가 요구하는 실행 알림과 중단 수단을 제공한다. 목적에 맞지 않는 서비스 유형으로 무제한 실행을 우회하지 않는다.
- Android 서비스 실행과 Wi-Fi 검색·AP 선택 권한은 별개다. 서비스가 실행 중이어도 검색 빈도·위치 접근·화면 꺼짐·제조사 배터리 정책의 제약을 받으며, 최종 연결은 OS가 결정한다. 네트워크 제안 등록, 연결 변경 이벤트와 이미 생성된 검색 결과를 우선 활용한다.
- 학교 네트워크가 보이지 않으면 낮은 활동 상태로 대기한다. 빈번한 전체 검색·속도 검사·위치 추적을 기본 동작으로 삼지 않는다.
- 자동 관리 중단은 앱의 측정과 연결 요청을 멈춘다. 사용자의 현재 OS 와이파이 연결을 임의로 끊지 않는다. 이미 등록된 설정에 대한 OS의 자체 자동 연결은 구분해서 안내한다.
- 화면을 내리는 동작과 OS 강제 종료·서비스 중단·절전·재부팅은 구분한다. 강제 종료나 기기 절전 중에도 앱이 계속 실행된다고 약속하지 않는다. 재개 시 실제 연결과 설정 상태를 다시 확인한다.
- Windows 로그인 시 자동 시작과 Android 재부팅 후 자동 재시작은 현재 확정된 사용자 요구가 아니다. 첫 버전은 사용자가 앱에서 시작한 관리 세션을 기준으로 검증하고, 부팅 자동 시작은 별도 사용자 선택과 OS 조건을 확인한 뒤 결정한다.

### 와이파이 도감 — 게임으로 즐기는 수집 요소

각 와이파이를 재미있는 이름과 캐릭터가 있는 수집 대상으로 표현한다. 미발견 그림을 회색으로 보여주는 방식은 사용자 요구다. 다음의 해금 연출과 세부 내용은 화면 시안으로 제안한다.

- 미발견 항목은 회색 캐릭터 실루엣과 가려진 이름으로 표시한다. 발견 후 컬러 그림·별명·짧은 설정을 공개하는 방식을 제안한다.
- 학교 공간의 특징을 살린 별명을 붙인다. 현재 시안에는 쉿파이, 밥도둑 핑핑이, 밤샘 패킷몬, 이불 밖은 버퍼링을 사용한다. 운영용 전체 이름 목록을 확정한 것은 아니다.
- 캐릭터 상세는 그림과 별명·수집 상태를 중심으로 한다. 짧은 설정과 실제 만난 기록은 보조 정보이며, 지도·설치 장소·위치 힌트나 AP 기술 정보는 도감에 넣지 않는다.
- 도감 해금 사건은 실제 연결 성공으로 확정했다. 운영체제가 등록된 학교 네트워크·AP에 연결했음을 확인한 뒤 수집 상태를 갱신한다. 주변 검색이나 신호 세기 관찰만으로는 해금하지 않는다. 기존 시안의 해금 버튼은 연출 확인용이며 실제 와이파이에 연결하지 않는다.
- 기술적인 접속 상태·실패 원인·신호 품질은 자동 관리와 관리자 기능에서 제공하며, 도감의 주 목적은 수집과 발견의 즐거움이다.
- 수집 기록에는 기존 자동 관리에서 얻은 실제 연결 결과를 활용한다. 도감 진행을 위해 연결 정책이나 측정 빈도를 변경하는 것은 기본 동작으로 삼지 않는다. 현재 연결을 유지하는 것이 적절하면 유지하고, 새로운 친구를 얻기 위한 강제 전환은 자동으로 수행하지 않는다.
- 2026-10-30 사용자 결정: 등록 AP 하나마다 캐릭터 하나를 둔다. 2026-11-01 변경: AP 항목은 물리 AP 하나이며 운영자가 그 장치의 여러 BSSID를 묶는다. 자동으로 묶지 않는다.
- 같은 내부 계정의 휴대폰·노트북은 수집 상태를 공유한다. 로그인 수단이 다른 계정을 이름·이메일로 자동 병합하지 않는다. 공개 순위·보상은 첫 출시 범위에 넣지 않는다.
- 2026-10-31 사용자 결정: 캐릭터 그림은 운영자가 등록한다. 별명과 그림이 모두 등록된 활성 AP만 공개 캐릭터이며, 공개 캐릭터가 아닌 AP는 사용자 도감과 진행률에 나오지 않고 연결해도 수집되지 않는다. 공개 전 연결은 소급해 수집하지 않는다. 비공개·비활성화해도 이미 수집한 기록은 보존한다.

### 검토용 화면 시안

학생 도감과 관리자 위치 조회 화면을 하나의 로컬 시안에서 전환해 검토한다. 캐릭터 해금, AP 선택, 예시 위치 수정은 시안 내부 상태만 바꾼다. 실제 로그인·설정 배포·와이파이 제어·운영 데이터 저장은 구현한 것이 아니다. 도감의 캐릭터는 생성한 이미지 자산을 활용한다.

## 7. 품질 판단과 측정 정책

### 연결 전에 알 수 있는 정보

주변 검색에서 얻은 신호 세기, 주파수 대역, 지원되는 연결 정보와 해당 AP의 과거 사용 기록을 활용한다. 신호가 강하다는 이유만으로 현재 인터넷 속도가 가장 빠르다고 표시하지 않는다.

과거 측정은 시각과 함께 저장하고 오래된 기록의 영향은 줄인다. 서로 다른 기기의 측정 결과를 동일한 성능으로 간주하지 않는다.

### 연결한 뒤 알 수 있는 정보

인터넷 접근 가능 여부, 작은 요청의 응답 지연과 실패, 사용 중 확인할 수 있는 연결 품질을 기록한다. 응답 지연을 다운로드 처리량으로 표현하지 않는다.

짧은 데이터 전송 검사는 필요한 경우나 사용자의 수동 검사에만 수행한다. 검사 시간·전송량에 상한을 두며, 제한된 표본을 최대 인터넷 속도의 정확한 측정치로 광고하지 않는다.

### 전환 안정성

- 후보가 잠시 강해졌다는 이유로 바로 전환하지 않는다.
- 현재 상태가 나쁜 기간, 후보의 개선 폭, 마지막 전환 시각을 함께 본다.
- 전환 후 대기 시간과 반복 실패 후보의 일시 제외를 적용한다.
- 임계값과 가중치는 현장 데이터로 조정할 구현 항목이다.
- 로그인 서버의 장애 하나만으로 학교 와이파이 전체가 나쁘다고 판단하지 않는다.
- 학교 전체의 상위 인터넷 회선이 혼잡하면 AP 이동만으로 개선되지 않을 수 있다.

## 8. 플랫폼별 구현 가능 범위

### Windows · C#

- Native Wi-Fi API를 이용해 네트워크·BSS 정보를 조회하고 프로필 기반 연결을 요청한다.
- 원하는 BSSID 목록을 연결 요청에 포함하는 기능을 검증할 수 있다. 특정 AP의 영구 고정이나 모든 하드웨어에서 동일한 전환을 보장하지 않는다.
- 최신 Windows의 위치 접근 동의와 학교·기기 정책 제한을 정상적인 권한 안내로 처리한다.
- OS·드라이버의 자체 로밍과 충돌하지 않게 자동 관리 주기를 설계한다.
- 자동 연결·전환은 요청 후 알림과 실제 연결 상태로 결과를 확인한다.

### Android · Kotlin

- 일반 사용자가 설치하는 앱 기준으로 설계한다. 루팅·제조사 시스템 권한·학교 소유 관리기기를 전제로 하지 않는다.
- Wi-Fi suggestion API로 인터넷 접속용 후보와 자격증명을 제공한다. 최종 네트워크·AP 선택은 Android가 수행한다.
- 필요하면 사용자 승인을 거쳐 저장 네트워크를 추가하는 공식 흐름을 검토한다.
- 기기 전체 인터넷 연결의 강제 전환에 peer-to-peer용 Network Request API를 대용하지 않는다.
- 자체 스캔을 반복하지 않고 허용된 최신 검색 결과를 활용한다. 검색 빈도 제한, 권한, 화면이 꺼진 상태와 제조사별 동작을 검증한다.
- 앱을 설치하기만 하면 매 순간 가장 강한 AP로 반드시 바뀐다고 약속하지 않는다.
- 관리자 웹에서 정보를 미리 등록하는 방식도 Android의 권한 제한을 없애지는 않는다.

### 관리자 웹과 서버

- 웹은 로그인, 네트워크 관리, 개인 코드 관리, 기본 상태 확인을 담당한다.
- 일반 브라우저가 학생 기기의 주변 AP 검색과 기기 전체 연결 제어를 직접 수행하는 구조로 만들지 않는다.
- 서버는 인증·권한·설정 배포를 담당하고, 학생 기기의 실시간 후보 판단은 앱과 OS에서 수행한다.
- 설정 배포와 연결 판단을 분리해, 서버가 잠시 중단돼도 기기에 저장된 설정과 OS 연결을 사용할 수 있게 한다.

## 9. 초기 인터넷 연결과 오프라인 동작

처음 설치·로그인·이메일 인증·설정 다운로드에는 서버에 연결할 인터넷이 필요하다. 기존 인터넷, 모바일 데이터 또는 다른 연결 수단을 사용한다. 아직 인터넷도 없고 설정도 내려받지 않은 기기에서 초대코드 입력만으로 학교 비밀번호를 알아내는 기능은 제공하지 않는다.

이미 설정을 받은 기기는 서버에 일시적으로 접속하지 못해도 저장된 설정과 OS 기능으로 연결을 계속 지원한다. 새 계정 로그인, 새 코드 검증, DataGSM 인증, 변경된 비밀번호 수신은 필요한 서버에 다시 연결한 뒤 수행한다.

설정 만료·오프라인 보관 기간과 권한 회수의 반영 시점은 구현 계획에서 정하고, 화면에 마지막 동기화 시간을 표시한다. 서비스 세션 만료만으로 진행 중인 OS 와이파이 연결을 강제로 끊지 않는다.

## 10. 첫 버전의 범위

포함:

- 관리자 한 명의 로그인과 서버 권한 검사
- 학교 이메일 인증, 개인 초대코드 로그인, DataGSM OAuth 로그인 (2026-10-31: 세 가지 모두 첫 출시 조건)
- 로그인 상태에서 다른 인증 수단을 새로 인증해 연결하는 사용자 주도 계정 연결
- 기기별 세션과 코드 발급·회수
- 학교 네트워크 등록·수정·비활성화와 설정 동기화
- Windows 앱의 주변 조회·연결 요청·결과 확인
- Android 앱의 설정 제공·후보 제안·권한 안내
- 신호·최근 기록을 활용한 후보 비교와 반복 전환 억제
- 마지막 동기화, 연결 결과와 실패 이유 표시
- 제한된 수동 품질 검사
- 앱 화면과 분리된 자동 관리 실행, Windows 트레이 제어, Android에서 허용되는 실행 상태 안내와 중단 수단
- 와이파이 도감: 등록 AP마다 캐릭터 하나, OS가 확인한 실제 연결로 해금, 같은 내부 계정의 기기 간 수집 상태 공유
- 관리자에서 전체 AP 설치 위치 조회, 건물·층·장소 등록과 위치 미등록 항목 확인

후속 범위:

- 공개 서비스 소개·다운로드 페이지의 완성도 향상
- 이용자가 별도로 동의하는 경우의 집계 품질 통계, 관리자 웹 전용 학교 설치 지도
- 추가 관리자, 이름·이메일 기반 자동 계정 병합(계속 제외)
- Play 스토어 배포 검토(시범 운영까지는 직접 설치 파일, 2026-11-01)
- 학교 AP·네트워크 제어 인프라와의 직접 통합

첫 버전은 전체 학생의 이동 경로나 AP별 실시간 위치를 중앙에 수집하는 서비스로 만들지 않는다. 연결 판단에 필요한 이력은 우선 기기에서 관리한다. 비밀정보와 개인 식별 정보가 없는 진단 자료를 사용자가 선택해 제공하는 범위는 구현 계획에서 정한다.

## 11. 검증 순서와 출시 판단

### 먼저 확인할 현장 조건

- 와이파이 목록이 여러 SSID인지, 하나의 SSID 아래 여러 AP인지 확인한다.
- 외부 공인 IP가 같다는 사실로 내부 IP 유지·같은 서브넷·무중단 로밍을 추정하지 않는다.
- 학교 네트워크의 보안 방식, 추가 로그인 페이지 유무, 정상 동작하는 접속정보를 확인한다.
- 실제 Android 기기와 Windows 어댑터에서 주변 검색·사용자 승인·연결 요청 동작을 확인한다.
- Windows 창 최소화·닫기·재열기 중 연결 관리가 이어지고 관리 엔진이 중복 실행되지 않는지 확인한다. Android에서 홈 화면 이동·화면 꺼짐·절전·OS 서비스 중단 상황의 관리 범위와 상태 표시를 확인한다.
- s로 시작하는 gsm.hs.kr 메일 계정이 실제로 인증 메일을 수신할 수 있는지 확인한다.
- DataGSM 클라이언트 등록 권한과 리다이렉트 URI 조건을 확인하고, 실제 학생 계정으로 인증·취소·거부·앱 복귀·사용자 정보 조회를 검증한다. 문서 확인만으로 실제 서비스 계정에서 로그인이 끝까지 검증됐다고 간주하지 않는다.

이 항목은 현재 답이 없어도 기획할 수 있는 현장 검증 항목이다. 현재 문서에서 학교가 단일 SSID라고 가정해 개발하지 않는다. 여러 SSID와 같은 SSID의 AP 이동을 구분하는 데이터 모델을 사용하고, Android의 세부 지원 범위는 실기기 결과로 결정한다.

### 실험에서 비교할 것

같은 기기·경로·비슷한 시간대에서 OS 기본 자동 연결 상태와 앱 사용 상태를 비교한다.

- 학생이 비밀번호를 직접 입력한 횟수
- 사용자가 수동으로 네트워크를 바꾼 횟수
- 연결에 걸린 시간과 연결 실패
- 전환 전후의 응답 지연·요청 실패·인터넷 이용 가능 여부
- 짧은 시간의 반복 전환 횟수
- 측정용 전송량과 휴대폰 배터리 부담

신호 표시가 좋아진 것만으로 서비스가 빨라졌다고 결론 내리지 않는다. Android가 선택 제안을 적용하지 않거나 기본 OS보다 개선이 없다면, 해당 플랫폼의 약속을 자동 전환에서 설정 배포·상태 안내 중심으로 조정한 뒤 출시 범위를 다시 검토한다.

## 12. 구현 계획 작성자에게 남기는 결정

다음은 사용자에게 다시 물어야 하는 제품 요구가 아니라 구현 계획에서 근거를 가지고 정할 항목이다.

- TypeScript 웹·서버 프레임워크와 데이터베이스 제품
- 메일 발송 제공업체, 운영 호스팅과 필요한 계정·비밀값 준비 절차
- 관리자 인증·복구 구현과 초기 관리자 등록 절차
- DataGSM 클라이언트 등록, 최소 권한과 사용자 정보 필드 검증, HTTPS 콜백 및 네이티브 앱으로 돌아오는 일회용 교환 방식
- API 세부 경로, 데이터 스키마와 설정 버전 형식
- 인증번호·세션·초대코드의 구체 수명, 재시도 제한과 회수 반영 방식
- OS 보안 저장소 연결과 서버 암호화 키 관리 방식
- 품질 점수의 가중치, 검색 주기, 전환 임계값·대기 시간
- 네이티브 API 래퍼, 앱 UI 도구와 배포 패키징
- Windows 트레이 프로세스의 수명, Android foreground service의 목적에 맞는 유형·시작 조건·권한·알림, 화면과 분리된 관리 엔진과 복구 흐름
- 오프라인 설정의 유효기간과 동기화 실패 처리

설정 배포를 할 수 있는 인증된 API, 암호화 저장, 회수 가능한 세션을 첫 서버 설계에 포함한다. 실제 메일 발송·외부 서비스 생성·운영 배포는 이 기획서 작성 과정에서 수행하지 않는다.
