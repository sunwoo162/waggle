# 남은 제품 개발 순서

사용자의 전체 개발 진행 지시를 적용한다. 각 단계는 기능 브랜치·동작 검사·독립 리뷰·PR·CI를 거치며 완료 후 다음 단계로 이어간다. 기존 승인을 다시 묻지 않는다. 실계정·교내 실기기·실제 배포처럼 외부 환경이 필요한 결과는 코드·합성 검증과 구분한다.

2026-10-31 기획 개정을 반영했다. 기준 문서: [기획 총괄표](../../product/project-planning.md).

## 확정한 제품 기준

- GSM 한 곳 전용. 관리자 웹과 Android·Windows 일반 사용자 앱을 구분한다.
- 등록한 AP 항목 하나에 캐릭터 하나다. 현재 AP 항목은 BSSID 하나로 식별하며 물리 장치의 여러 BSSID는 별도 등록 항목이다.
- 별명과 그림이 모두 등록된 활성 AP만 공개 캐릭터다. 공개 캐릭터가 아닌 AP는 앱 도감과 진행률에 나오지 않고 수집되지 않는다. 공개 전 연결을 소급해 수집하지 않는다.
- 동일 내부 계정의 휴대폰·노트북은 수집 상태를 공유한다. 이름·이메일 일치로 서로 다른 인증 계정을 자동 병합하지 않는다.
- 로그인한 사용자가 다른 로그인 수단을 그 자리에서 새로 인증해 같은 계정에 연결할 수 있다. 이미 다른 계정에 묶인 수단이면 사용자 확인 후 수집 집합을 합집합으로 합친다.
- DataGSM·학교 이메일·개인 코드 세 가지 로그인이 모두 첫 출시(교내 시범 운영) 조건이다.
- 기획 의도는 학교 Wi-Fi 비밀번호 입력 없애기와 약한 AP에 붙어 느려지는 문제 줄이기다. 도감은 이용 동기이며, 위치 권한을 거절해도 비밀번호 없는 연결은 동작해야 한다.
- 사용자 도감은 캐릭터 그림·재미있는 이름·회색 미발견 중심이다. 지도·설치 위치는 관리자 웹에서만 제공한다.
- OS가 확인한 실제 연결의 SSID·BSSID·보안 방식과 등록 AP가 맞을 때 수집한다. 서버는 인증된 앱의 연결 보고를 받으며 이를 독립적인 무선 접속 증명으로 과장하지 않는다.
- 중앙 수집은 사용자별 발견 AP 집합이다. 학생별 이동 경로·반복 접속 시각·기기별 AP 이동 이력을 저장하지 않는다.
- 배포 방식(직접 설치 파일 / Play 스토어)과 부팅 자동 시작은 미정이다. 임의로 확정하지 않는다.

## 단계

- [x] 인증된 학교 설정 배포: 활성 네트워크의 접속정보와 AP 식별자만 전달하고 지도·설치 장소는 제외. Windows 보호 캐시와 인증된 동기화 코어. PR #20 병합.
- [x] 관리자 캐릭터·도감 동기화: AP별 이미지·별명 편집, 실제 연결 보고와 중복 없는 사용자별 수집 집합. 이미지 업로드와 안전한 정적 제공. PR #21 병합.
- [ ] Windows 실제 연결 엔진 (PR #23): Native Wi-Fi 어댑터, 안정성 중심 후보 판단, 프로필 등록·연결 요청·OS 확인, 트레이·중지·실패 복구, 그림 도감. 남은 리뷰 지적 2건을 실패 검사부터 수정한다.
  - 서버 재확인(/me 이후 /config·/encyclopedia·/collection) 실패 뒤 정상 전체 재확인 전까지 관찰·연결을 재개하지 않는 명시적 중단 상태. RateLimited 300초 대기 유지.
  - 캐릭터가 사라지거나 Collection이 null이 되면 열린 상세를 닫고 DataContext 정리.
- [ ] 캐릭터 공개 조건: 서버 도감 API는 별명·그림이 모두 있는 활성 AP만 반환하고, 수집 보고도 공개 캐릭터만 받는다. 관리자 캐릭터 화면에 공개/미공개 상태 표시. Windows 앱은 받은 목록만 표시·보고. 기존 수집 기록은 보존.
- [ ] Android 앱: Kotlin·Compose, 코드 로그인·Keystore 보호 저장·설정 동기화, Wi-Fi suggestion·권한·허용되는 백그라운드 실행·연결 관찰·그림 도감. Gradle 검사·CI. 단계 초반에 배포 방식 결정을 사용자에게 요청한다(권한·서비스 종류 심사 조건에 영향). 실현 방식은 [Android Wi-Fi 실현 방식](../../research/2026-10-31-android-wifi-feasibility.md)을 따른다.
  - 본 개발 전 실기기 시험 앱: BSSID 지정 재등록으로 AP 유도가 되는지, 위치 권한 없이 자동 연결되는지, OS 기본 로밍 기준값. 결과로 약한 AP 대응 방식(유도 또는 안내)을 정한다.
  - minSdk 31·target 36, SSID 단위 suggestion(평소 BSSID 미지정)과 승인 상태 표시, 설정 버전 변경 시 재등록·제거. 이 연결 기능은 위치 권한 없이 먼저 완성한다.
  - 약한 연결 감지(RSSI·링크 속도)와 OS 스캔 결과 읽기, 시험 결과에 따른 유도 또는 알림.
  - FLAG_INCLUDE_LOCATION_INFO NetworkCallback 관찰, 가려진 값 거부, SSID·BSSID·보안 방식 정확 일치만 수집.
  - location 유형 포그라운드 서비스와 상시 알림. 백그라운드 위치·부팅 수신·직접 스캔 없음.
  - 순수 판정 로직(가림 판정, 보안 방식 매핑, AP 일치)은 JVM 단위 테스트로 먼저 실패시킨 뒤 구현한다. OS 어댑터는 인터페이스로 분리해 합성 어댑터로 흐름을 검사한다.
  - 7절 실기기 확인 항목은 실기기를 확보한 뒤 기록하고, 합성 검증을 실기기 결과로 표시하지 않는다.
- [ ] 나머지 인증: DataGSM 일반 사용자·네이티브 복귀, 학교 이메일 인증번호와 발송 어댑터. 미등록 OAuth·미설정 메일은 실제 성공으로 표시하지 않음.
- [ ] 계정 연결: 로그인 상태에서 수단 추가(새로 인증), 수단별 한 개, 다른 계정에 묶인 수단은 사용자 확인 후 합집합 병합과 상대 계정 세션 회수, 마지막 수단 해제 금지. 관리자 조회·해제. 두 앱의 내 계정 화면.
- [ ] 계정 수명주기: 사용자 요청·운영자 실행 계정 삭제(수단·세션·수집 집합), 비재학 계정 정리 절차.
- [ ] 관리자 전용 위치 시각화: 도면 등록과 AP 위치 표시·편집. 실제 도면 등록 전에는 예시 지도를 학교 도면처럼 쓰지 않음.
- [ ] 운영 마무리: 배포 방식에 맞는 서명·설치 안내, 백업·복구, 운영자 교체 절차, 교내 검증·시범 운영 계획.

## 실제 확인에 필요한 외부 조건

DataGSM 클라이언트 등록·정확한 운영자 ID, 학교 이메일 발송 서비스와 수신 확인, 실제 학교 네트워크/AP·접속정보·도면, Android 실기기, 운영 HTTPS 서버와 서명·설치 배포 조건이 필요하다. 세 가지 로그인이 모두 출시 조건이므로 이 조건이 준비되기 전에는 시범 운영을 시작하지 않는다. 코드에 인증 우회·가짜 성공 모드를 추가해 이를 대체하지 않는다.
