# 와글 프로젝트 기획 총괄표

작성일: 2026-10-29 · 개정: 2026-10-31  
상태: 관리자 웹·공통 서버(운영자 인증, 네트워크/AP, 개인 코드·기기 세션, 설정 배포, AP별 캐릭터·계정 수집)는 main에 병합됐다. Windows 자동 관리·그림 도감은 PR #23에서 리뷰 수정 중이다. Android 앱, DataGSM·학교 이메일 로그인, 계정 연결, 관리자 지도는 아직 구현하지 않았다. 실제 학교 Wi-Fi·실제 학생 계정·Android 실기기는 검증 전이다.  
상세 요구: [제품 기획서](../superpowers/specs/2026-10-29-campus-wifi-design.md)  
개발 순서: [남은 제품 개발 순서](../superpowers/plans/2026-10-30-remaining-development.md)

## 1. 제품의 중심

광주소프트웨어마이스터고등학교(GSM) 전용 서비스다. 학교는 한 곳으로 고정하며 학교 선택·추가·여러 학교 운영은 계획하지 않는다.

와글은 학교 Wi-Fi의 두 가지 불편을 해결하려고 만든다. 캐릭터 도감은 이 기능을 설치하고 켜 두게 만드는 동기다.

| 불편                    | 와글의 해결                                                                                | Windows                 | Android                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------ | ----------------------- | ---------------------------------------------------------------------------- |
| **비밀번호 입력**       | 앱이 학교 접속정보를 OS에 등록한다. 비밀번호가 바뀌어도 운영자가 고치면 앱이 다시 등록한다 | 해결                    | 해결 (처음 한 번 OS 허용)                                                    |
| **약한 AP에 붙어 느림** | 지금 AP가 계속 약하고 더 나은 학교 AP가 있으면 옮긴다                                      | 앱이 비교하고 직접 전환 | OS 로밍에 맡기고, 앱은 더 나은 AP 쪽으로 유도하거나 다시 연결을 안내 (7.1절) |
| 학교 회선 자체의 혼잡   | 해결 대상이 아니다. 앱이 대역폭을 늘릴 수 없다                                             | -                       | -                                                                            |

**이용 동기**: 실제로 연결한 학교 AP마다 캐릭터를 모으는 도감으로 앱을 계속 켜 둘 이유를 만든다. 도감 때문에 연결 관리 판단을 바꾸지 않는다.

우선순위는 비밀번호 없는 연결 → 약한 AP 탈출 → 도감 순이다. 위치 권한을 거절해도 비밀번호 없는 연결은 동작해야 한다.

학생은 처음 로그인과 권한 설정을 마친 뒤 자동 관리를 한 번 켠다. 그 뒤에는 앱 화면을 닫아도 OS가 허용하는 범위에서 연결 관리가 이어진다. 운영자 한 명은 관리자 웹에서 학교 네트워크·AP·캐릭터·사용자 코드를 관리한다. 사용자 앱에는 지도·도면·AP 설치 위치가 없고, 이 기능은 관리자 웹에만 있다.

## 2. 확정 사항

### 2.1 사용자가 확정한 요구

| 항목          | 확정 내용                                                                                     |
| ------------- | --------------------------------------------------------------------------------------------- |
| 대상          | GSM 교내 이용자, Android 휴대폰·Windows 노트북                                                |
| 구현 언어     | Android Kotlin, Windows C#, 관리자 웹·서버 TypeScript                                         |
| 관리자        | 사전 지정한 운영자 한 명. 관리자 화면은 웹                                                    |
| 네트워크 설정 | 관리자가 정확한 SSID·보안 방식·비밀번호와 AP(BSSID)를 등록                                    |
| 학생 이용     | 비밀번호를 직접 입력하지 않고, 연결 선택을 자동화                                             |
| 실행 방식     | 초기 설정 후 자동 관리를 켜면 화면 밖에서도 OS가 허용하는 범위에서 실행                       |
| 학생 로그인   | DataGSM / 학교 이메일 / 개인 코드. **첫 출시에 세 가지 모두 포함** (2026-10-31)               |
| 학교 이메일   | 로컬 부분이 s로 시작, 도메인은 정확히 gsm.hs.kr                                               |
| 개인 코드     | 한 사람에게 하나 발급, 코드만 입력해 로그인, 본인의 휴대폰과 노트북에서 사용                  |
| 계정 연결     | 로그인한 상태에서 사용자가 다른 로그인 수단을 직접 추가 인증해 같은 계정에 연결 (2026-10-31)  |
| 자동 병합     | 이름·이메일이 같다는 이유로 계정을 자동으로 합치지 않음                                       |
| 도감          | 캐릭터 그림·재미있는 이름·수집 상태 중심. 미발견은 회색. 사용자 앱에는 지도 없음              |
| 도감 해금     | OS가 확인한 실제 연결의 SSID·BSSID·보안 방식이 등록 AP와 맞을 때만 해금                       |
| 수집 단위     | 등록 AP 하나(BSSID 하나)에 캐릭터 하나                                                        |
| 캐릭터 제작   | 운영자가 그림·별명을 등록. **그림이 없는 AP는 도감에 보이지 않고 수집되지 않음** (2026-10-31) |
| 기기 간 도감  | 같은 내부 계정의 휴대폰·노트북에서 수집 상태 공유                                             |
| 관리자 위치   | 전체 AP의 건물·층·장소 조회. 지도·도면·설치 위치 관리는 관리자 웹 전용                        |
| 운영자 권한   | DataGSM ADMIN 역할은 와글 관리자 권한이 아님. 사전 지정 운영자 ID만 허용                      |
| 디자인        | 사용자 제공 BASE 색·타입·간격·모션 체계, 한국어 UI, 과한 장식 배제                            |

### 2.2 하지 않는 것

- 여러 학교 지원과 그 확장 계획.
- 사용자 앱의 지도·도면·AP 위치 힌트.
- 학생 이동 경로, 반복 접속 시각, 기기별 AP 방문 이력의 중앙 수집.
- Android의 강제 네트워크 전환이나 무중단 연결 약속.
- 스캔·연결 요청·실패·시간 초과만으로 도감 해금.
- 도감을 채우려고 정상 연결을 강제로 바꾸는 자동 동작.
- 인증 우회나 가짜 성공 모드로 외부 조건(OAuth 등록, 메일 발송, 실제 학교 Wi-Fi)을 대신하는 것.
- 공개 순위·아이템 상점·게임 화폐, 추가 관리자, 급식·시간표, 학교 네트워크 장비와의 직접 통합.

## 3. 첫 출시 범위

"첫 출시"는 교내 시범 운영을 시작할 수 있는 상태를 뜻한다. 아래 항목이 모두 갖춰져야 한다.

### 일반 사용자 앱 (Android·Windows 공통)

- 세 가지 로그인: DataGSM, 학교 이메일 인증번호, 개인 코드.
- 내 계정 화면에서 다른 로그인 수단 추가·해제 (5절).
- 필요한 권한·네트워크 등록 안내와 동의.
- 학교 설정과 도감 동기화, 마지막 동기화 시각 표시.
- 자동 관리 시작·일시 중지와 현재 상태, 사용자가 해야 할 조치 표시.
- 실제 연결 관찰 → 등록 AP 일치 시 수집 → 조용한 알림 → 앱을 열면 컬러 해금 연출.
- 그림 도감(목록·상세), 발견 수/공개 캐릭터 수 표시.
- 기기 안에만 보관하는 최근 연결 결과와 실패 이유.
- 로그아웃 시 이 기기의 보호 저장 정보 정리.
- Windows: 트레이 실행·다시 열기·종료, 중복 실행 방지.
- Android: OS가 요구하는 실행 알림과 중지 수단.

### 관리자 웹

- 사전 지정 운영자 한 명의 DataGSM 인증.
- 네트워크와 접속정보 등록·수정·비활성화 (서버 암호화 저장).
- AP(BSSID) 등록과 건물·층·설치 장소 관리, 위치 미등록 항목 확인.
- 도면 위 AP 설치 위치 표시와 편집.
- AP별 캐릭터 별명·소개·그림 등록, 공개 상태 확인.
- 개인 코드 발급·회수·재발급, 코드에 연결된 계정 확인.
- 일반 사용자 계정의 로그인 수단·기기 세션 조회와 회수.

### 출시 차단 조건 (외부)

세 가지 로그인을 모두 첫 출시에 넣기로 했으므로, 아래 외부 조건이 준비되기 전에는 시범 운영을 시작하지 않는다. 개발 중 운영자 본인의 점검은 개인 코드로 할 수 있지만 이를 출시로 표현하지 않는다.

- DataGSM OAuth 클라이언트 등록, 리다이렉트 URI, 정확한 운영자 ID.
- 학교 이메일 발송 서비스 설정과 gsm.hs.kr 메일함의 실제 수신 확인.
- 실제 학교 SSID·보안 방식·비밀번호·AP BSSID, 설치 장소, 도면.
- 운영 HTTPS 서버와 백업.
- 배포 방식 결정과 그에 맞는 서명 (10절).

## 4. 핵심 사용 흐름

### 4.1 처음 사용

1. 앱을 설치하고 DataGSM, 학교 이메일, 개인 코드 중 하나로 로그인한다.
2. 앱이 필요한 권한과 이유를 안내하고, 사용자가 OS 동의 화면에서 승인한다.
3. 인증된 세션으로 학교 설정과 도감을 받는다. 처음 한 번은 인터넷(모바일 데이터 등)이 필요하다.
4. 자동 관리를 켠다.

### 4.2 평소 사용

5. 앱이나 OS가 현재 연결과 학교 네트워크 후보를 확인한다. 현재 연결이 괜찮으면 그대로 둔다.
6. OS가 등록 AP에 실제로 연결했음을 확인하면 해당 캐릭터를 처음 한 번 수집한다.
7. 새 수집이면 조용한 알림을 보내고, 사용자가 앱을 열 때 컬러 해금 연출을 보여준다.
8. 같은 계정의 다른 기기도 다음 동기화 때 같은 수집 상태를 보여준다.

### 4.3 두 번째 기기와 다른 로그인 수단

- 같은 수단으로 로그인하면 같은 계정이다. 예: 같은 개인 코드를 휴대폰과 노트북에 입력.
- 다른 수단을 쓰고 싶으면 먼저 기존 계정으로 로그인한 기기에서 그 수단을 추가 인증해 연결한다. 그 뒤에는 어느 수단으로 로그인해도 같은 계정이다.
- 연결하지 않고 다른 수단으로 로그인하면 별도 계정이 생긴다. 로그인 화면과 내 계정 화면에서 이 점을 안내한다.

DataGSM 인증 성공은 학교 Wi-Fi 연결 성공과 다른 사건이다. 앱을 켰을 때 이미 등록 AP에 연결돼 있다면 현재 연결을 실제로 확인한 뒤 수집할 수 있다. 앱이 관찰하지 않은 과거 연결을 수집으로 만들지 않는다.

## 5. 계정과 로그인 수단

### 5.1 로그인 수단별 규칙

| 수단        | 확인하는 것                                                                    | 계정 식별 기준          |
| ----------- | ------------------------------------------------------------------------------ | ----------------------- |
| DataGSM     | OAuth(Authorization Code + PKCE), 활성 재학생 상태. 졸업·자퇴 등 비재학은 거부 | DataGSM 사용자 고유 ID  |
| 학교 이메일 | s로 시작하는 정확한 gsm.hs.kr 주소, 메일로 보낸 일회용 인증번호                | 검증된 이메일 주소      |
| 개인 코드   | 운영자가 발급한 유효한 코드(회수·재발급 버전 확인)                             | 코드가 연결된 내부 계정 |

세 수단 모두 로그인 결과로 와글의 기기 세션을 발급한다. DataGSM 토큰을 와글 API 세션으로 쓰지 않는다. 일반 사용자 인증은 별도 DB의 제한된 /api/client 경로만 사용한다.

### 5.2 계정 연결 (2026-10-31 결정)

사용자가 로그인한 상태에서 다른 수단을 직접 인증해 같은 계정에 연결한다. 아래 세부 규칙은 결정 방향에 따른 기획 제안이다.

- **시작 조건**: 유효한 기기 세션이 있는 상태에서 내 계정 → 로그인 수단 → 추가를 선택한다.
- **새로 인증**: 추가할 수단은 그 자리에서 다시 인증한다(DataGSM 재인증, 이메일 인증번호, 개인 코드 입력). 저장된 정보나 이름·이메일 비교로 대신하지 않는다.
- **수단별 한 개**: 한 계정에는 DataGSM 1개, 이메일 1개, 개인 코드 1개까지 연결한다.
- **아무 계정에도 없는 수단**: 현재 계정에 바로 추가한다.
- **이미 다른 계정에 있는 수단**: 두 계정의 수단을 방금 모두 인증했으므로 "두 계정 합치기" 확인 화면을 보여준다. 사용자가 확인하면 수집 집합을 합집합으로 합치고 현재 계정을 남긴다. 다른 계정의 기기 세션은 회수하고, 그 기기는 다시 로그인하면 합쳐진 계정으로 들어온다. 사용자가 확인하지 않으면 아무것도 바꾸지 않는다.
- **해제**: 마지막 남은 수단은 해제할 수 없다. 해제해도 수집 기록은 계정에 남고 나누지 않는다.
- **관리자**: 계정별 연결 수단과 연결·합치기 시각을 조회하고, 잘못 연결된 수단을 해제할 수 있다. 코드 원문·인증번호·토큰은 기록하지 않는다.
- **자동 병합 금지 유지**: 서버가 이름·이메일·학번을 근거로 먼저 합치거나 합치기를 권하지 않는다.

### 5.3 개인 코드

- 운영자가 한 사람에게 하나 발급하고 대상 구분용 별칭을 붙인다. 원문은 발급할 때만 보여준다.
- 코드만 입력해 로그인한다. 코드를 가진 사람이 로그인할 수 있는 자격증명이므로 전달 경로를 운영 안내에 적는다.
- 회수하면 연결된 기기 세션 갱신이 막힌다. 재발급하면 이전 코드는 쓸 수 없다.
- 선생님이나 DataGSM 재학생 조건에 맞지 않는 이용자는 개인 코드를 사용한다.

### 5.4 운영자

- 사전 지정 운영자 ID 한 개만 관리자 웹에 들어온다. DataGSM ADMIN 역할로 자동 승격하지 않는다.
- 운영자 교체는 서버 운영 설정을 바꾸는 절차로만 한다. 관리자 웹에 운영자 추가·초대 기능은 없다.

## 6. 연결과 수집 규칙

### 6.1 연결 관리

- 현재 연결이 충분하면 유지한다.
- 상태가 계속 나쁘고 더 유리한 후보가 있으면 전환을 시도하거나 OS에 후보를 제공한다.
- 전환 후에는 대기 시간을 두고, 반복 실패한 후보는 잠시 제외한다.
- 모든 후보의 속도를 반복 측정하지 않는다. 신호와 최근 결과로 후보를 좁힌다.
- 자동 관리를 중지하면 앱의 측정·연결 요청을 멈춘다. 현재 OS Wi-Fi 연결은 끊지 않는다.
- 서버 재확인이 실패하면 새 Wi-Fi 요청을 멈추고, 다음 정상 재확인이 끝난 뒤에만 다시 시작한다.

### 6.2 수집

- 해금 조건은 OS가 확인한 실제 연결의 SSID·BSSID·보안 방식이 **공개된 캐릭터가 있는** 등록 AP와 일치하는 것이다.
- 스캔에서 보임, 연결 요청 접수, suggestion 등록 성공, 연결 실패, 시간 초과는 해금이 아니다.
- 같은 계정의 같은 캐릭터는 한 번만 수집된다. 재연결·재시작으로 중복이 생기지 않는다.
- 오프라인에서 확인한 수집은 계정에 묶인 OS 보호 저장소에 보관했다가 서버에 중복 없이 보낸다.
- 서버에는 계정별 "발견한 AP 집합"만 저장한다. 접속 시각·횟수·기기·순서는 저장하지 않는다.
- 서버는 인증된 앱의 보고를 검증하지만, 이것을 무선 접속의 독립적인 증명으로 표현하지 않는다.

### 6.3 캐릭터 공개 조건 (2026-10-31 결정)

- 운영자가 별명과 그림을 모두 등록한 활성 AP만 "공개 캐릭터"다.
- 공개 캐릭터가 아닌 AP는 사용자 도감 목록과 진행률 분모에 나오지 않고, 연결해도 수집되지 않는다.
- 나중에 그림을 등록해 공개하면, 그 뒤 실제 연결을 관찰했을 때 수집된다. 공개 전 연결을 소급해 수집하지 않는다.
- 공개 캐릭터를 비공개로 돌리거나 AP를 비활성화하면 앱 목록에서 사라지지만, 이미 수집한 기록은 보존하고 다시 공개하면 복원한다.
- 현재 구현은 그림이 없는 활성 AP도 "이름 없는 친구"로 앱에 내보낸다. 이 결정에 맞게 서버 도감 API와 앱을 고쳐야 한다(남은 개발 순서 참고).
- 듀얼 밴드 AP처럼 한 장치에 BSSID가 여러 개면 각각 별도 항목이다. 어느 BSSID에 캐릭터를 공개할지는 현장 조사 뒤 운영자가 정한다.

### 6.4 사용자 앱 도감 표시

- 목록: 공개 캐릭터만, 미발견은 회색 실루엣과 가려진 이름, 발견은 컬러 그림과 별명.
- 상세: 그림·별명·소개·수집 상태. 지도·설치 장소·SSID·BSSID 등 기술 정보는 넣지 않는다.
- 캐릭터가 비공개되거나 인증 상태를 잃으면 열린 상세를 닫고 이전 내용을 지운다.

## 7. 플랫폼별 약속

사용자에게 보여주는 문구는 아래 약속을 넘지 않는다.

| 항목          | Windows                                                 | Android                                                                     |
| ------------- | ------------------------------------------------------- | --------------------------------------------------------------------------- |
| 연결 방식     | Native Wi-Fi로 사용자 프로필 등록, BSSID 선호 연결 요청 | Wi-Fi suggestion 제공. 어느 네트워크에 붙을지는 OS가 결정                   |
| 약한 AP 대응  | 신호·최근 결과로 후보를 비교해 직접 전환                | OS 로밍 우선. 확인되면 더 나은 BSSID로 유도, 아니면 다시 연결 안내          |
| 사용자 문구   | "학교 Wi-Fi를 자동으로 연결하고 관리합니다"             | "비밀번호 없이 학교 Wi-Fi에 붙고, 약한 연결이면 알려드려요"                 |
| 화면 밖 실행  | 트레이 프로세스                                         | 목적에 맞는 서비스 종류와 실행 알림. 절전·제조사 정책으로 멈출 수 있음 안내 |
| 연결 관찰     | OS 연결 상태의 SSID·BSSID·보안 방식                     | NetworkCallback·WifiInfo. 권한이 부족하면 SSID·BSSID가 가려져 수집 불가     |
| 약속하지 않음 | 모든 드라이버에서 같은 전환                             | 강제 전환, 원하는 AP 고정, 무중단 연결                                      |

Android는 위치 권한 없이 SSID·BSSID가 가려질 수 있다. 권한이 부족하면 "도감 수집을 위해 위치 권한이 필요합니다"처럼 이유와 결과를 정확히 보여주고, 가려진 값으로 수집하지 않는다.

### 7.1 Android 실현 방식

공식 문서 근거와 세부 흐름은 [Android Wi-Fi 실현 방식](../research/2026-10-31-android-wifi-feasibility.md)에 정리했다. 요점:

- **등록**: 활성 네트워크마다 SSID 단위 suggestion을 앱 화면에서 등록하고 OS 승인을 받는다. BSSID는 지정하지 않아 OS 로밍을 막지 않는다. 등록 성공을 연결 성공으로 표시하지 않는다.
- **관찰**: NetworkCallback에 FLAG_INCLUDE_LOCATION_INFO를 붙여 연결된 Wi-Fi의 SSID·BSSID·보안 방식을 받는다. 정밀 위치 권한과 위치 설정이 필요하다. 가려진 값이면 수집하지 않는다.
- **화면 밖**: 관리를 켜면 앱 화면에서 location 유형 포그라운드 서비스를 시작하고 상시 알림을 띄운다. 백그라운드 위치 권한은 요청하지 않는다. 프로세스가 끝나면 앱을 다시 열어야 한다.
- **권한 단계**: 비밀번호 없는 연결은 Wi-Fi 등록 허용만 있으면 된다. 정밀 위치는 약한 AP 비교와 도감 수집에만 쓴다. 위치를 거절해도 연결 기능은 남긴다.
- **약한 AP 대응**: OS 로밍이 기본이다. 관리 중 현재 신호(RSSI·링크 속도, 위치 권한 불필요)가 일정 시간 나쁘면, OS가 이미 가진 스캔 결과에서 같은 학교 SSID의 더 강한 BSSID를 찾는다. ① 실험: suggestion을 그 BSSID로 잠시 갱신해 옮기도록 유도하고, 옮긴 뒤 BSSID 지정을 풀어 원래대로 돌린다. ② 실기기에서 ①이 안 되거나 위험하면: "더 가까운 학교 Wi-Fi가 있어요" 알림과 Wi-Fi 패널 바로가기만 제공한다. 어느 쪽을 쓸지는 Android 단계 첫 실기기 시험으로 정한다.
- **하지 않음**: 앱의 직접 스캔 요청(백그라운드 30분 1회 제한), BSSID 영구 고정, 사용자 저장 네트워크로 추가(ACTION_WIFI_ADD_NETWORKS는 앱이 이후 수정·삭제할 수 없음).
- **수집 경로 무관**: 학생이 직접 저장한 학교 Wi-Fi로 붙어도 OS가 확인한 연결이 등록 AP와 같으면 수집한다.
- **제안 기준**: 최소 Android 12(API 31), target 36. Android 11 이하는 지원하지 않는다.

## 8. 데이터와 개인정보

### 8.1 서버가 저장하는 것

| 데이터      | 내용                                                 | 보관              |
| ----------- | ---------------------------------------------------- | ----------------- |
| 계정        | 내부 ID, 상태                                        | 계정 삭제 시까지  |
| 로그인 수단 | DataGSM 고유 ID, 검증된 이메일, 개인 코드 다이제스트 | 해제·삭제 시 제거 |
| 기기 세션   | 플랫폼, 발급·갱신·회수 상태                          | 회수·만료 후 정리 |
| 수집 집합   | (계정, AP) 쌍만                                      | 계정 삭제 시까지  |
| 학교 설정   | 네트워크·접속정보(암호화)·AP·위치·도면·캐릭터        | 운영자가 관리     |

DataGSM 응답의 학급·기숙사 등 로그인에 필요 없는 학생 정보는 저장하지 않는다.

### 8.2 기기에만 저장하는 것

- 현재 신호, 최근 검색 결과, 최근 연결 결과·실패 이유.
- 오프라인용 승인된 설정, 서버로 보내지 않은 수집 보고.
- 세션과 학교 접속정보는 OS 보안 저장소(Windows DPAPI, Android Keystore)에 보관한다.

### 8.3 수명주기 (제안)

- **졸업·자퇴**: DataGSM 신규 로그인은 거부한다. 기존 계정은 학년 말에 운영자가 비활성화·삭제할 수 있다.
- **계정 삭제**: 사용자가 내 계정에서 요청하거나 운영자가 실행한다. 로그인 수단·세션·수집 집합을 함께 삭제한다. 백업에 남은 기간은 운영 안내에 적는다.
- **회수의 한계**: 코드·세션 회수는 와글 서비스 접근을 막을 뿐, 이미 OS에 저장된 학교 Wi-Fi 비밀번호를 무효화하지 않는다. 이를 화면에서 과장하지 않는다.

## 9. 검증과 시범 운영

### 9.1 검증 단계

| 단계      | 내용                                                             | 현재                    |
| --------- | ---------------------------------------------------------------- | ----------------------- |
| 자동 검사 | 서버·웹 테스트, Windows 테스트, Android Gradle 검사, CI          | 서버·웹·Windows 운영 중 |
| 합성 검증 | 실제 서버·DB·세션과 합성 Wi-Fi 어댑터로 전체 흐름 확인           | Windows 확인            |
| 실기기    | 실제 Windows 어댑터와 Android 기기에서 권한·관찰·백그라운드 확인 | 미검증                  |
| 교내 현장 | 실제 SSID 구조·인증 방식·BSSID·장시간 실행                       | 미검증                  |
| 시범 운영 | 소수 학생의 실제 사용                                            | 미시작                  |

합성 화면이나 테스트를 실제 학생·학교 Wi-Fi 사용 증거로 표현하지 않는다.

### 9.2 현장에서 먼저 확인할 것

- 학교 Wi-Fi가 여러 SSID인지, 같은 SSID 아래 여러 AP인지.
- 보안 방식(공유 비밀번호인지, 추가 로그인 화면이 있는지). **학교 Wi-Fi가 개인별 계정을 쓰는 WPA2/WPA3-Enterprise(802.1X)이거나 캡티브 포털이면 현재 설계(open·wpa2/wpa3-personal)로는 "비밀번호 0회"를 달성할 수 없다.** 이 경우 기획을 다시 검토하므로 가장 먼저 확인한다.
- 학교(정보부·담당 교사)가 앱으로 Wi-Fi 비밀번호를 배포하는 것을 허락하는지. OS에 등록된 비밀번호는 기기 관리자 권한이 있는 사용자가 꺼내 볼 수 있으므로(예: Windows 저장 프로필) "학생에게 비밀번호가 보이지 않음"을 보안 장치로 설명하지 않는다.
- AP별 BSSID 목록과 실제 설치 장소, 듀얼 밴드 여부.
- 외부 IP가 같다는 이유로 내부 로밍이 끊김 없다고 가정하지 않는다.

### 9.3 시범 운영안 (제안)

- 규모: 운영자 포함 5~10명, Android와 Windows 사용자를 섞는다.
- 기간: 1~2주.
- 확인할 것: 11절 성공 기준, 계정 연결 사용 여부, 권한 거절 비율, 배터리 부담, 도감 수집 수.
- 수집 방법: 사용자가 직접 보내는 진단 자료와 설문. 서버에 이동 경로나 접속 시각을 모으지 않는다.

## 10. 배포 (미정)

배포 방식은 아직 정하지 않았다. 결정에 필요한 조건만 정리한다. Android 권한·백그라운드 실행 방식이 배포 경로의 정책 심사에 영향을 주므로 Android 단계 초반에 결정한다.

| 방식                    | 장점                              | 필요한 것·제약                                                                                     |
| ----------------------- | --------------------------------- | -------------------------------------------------------------------------------------------------- |
| 직접 설치 파일          | 심사가 없어 시범 운영을 빨리 시작 | Android "출처를 알 수 없는 앱" 허용 안내, 업데이트 직접 배포, Windows 서명 없으면 SmartScreen 경고 |
| Play 스토어(+설치 파일) | 설치·업데이트가 쉬움              | 개발자 계정, 위치·백그라운드·서비스 종류 권한 심사, 앱 내 계정 삭제 요구                           |

어느 방식이든 Windows 설치 파일 서명과 업데이트 경로, Android 서명 키 보관을 운영 안내에 포함한다.

## 11. 성공 기준

핵심 지표 (기획 의도):

- **비밀번호 0회**: 최초 설정 이후 학생이 학교 Wi-Fi 비밀번호를 직접 입력하지 않는다. 설치부터 첫 학교 Wi-Fi 연결까지 걸린 시간을 잰다. 운영자가 비밀번호를 바꿔도 학생 조작 없이 다시 연결된다.
- **약한 AP 체류 감소**: 같은 기기·비슷한 이동 경로에서 와글을 켰을 때와 껐을 때(OS 기본 동작)를 비교해, 약한 신호에 머문 시간·수동 재연결 횟수·응답 지연이 줄었는지 확인한다. 개선이 없으면 그 플랫폼의 약속을 "비밀번호 없는 연결" 중심으로 낮춘다.
- 측정은 시범 운영 참여자 기기의 로컬 기록과 본인이 직접 보낸 진단 자료로만 한다. 서버에 이동·접속 기록을 모으지 않는다.

기능 기준:

- 세 가지 로그인 경로가 각각 일반 사용자 세션으로 이어진다.
- 다른 수단을 연결한 계정에서 휴대폰·노트북의 수집 상태가 일치한다.
- 앱 화면 밖에서 가능한 자동 관리 범위가 실제 상태와 일치하게 표시된다.
- 신호 발견·연결 요청·실패만으로는 해금되지 않고, 실제 연결 확인 때만 해금된다.
- 같은 계정의 같은 캐릭터가 중복 수집되지 않는다.
- 그림이 없는 AP는 사용자 도감에 보이지 않는다.
- 관리자는 주변에 보이지 않는 등록 AP와 위치 미등록 AP를 조회할 수 있다.
- 설정 변경·코드 회수·서버 장애·권한 거절 때 사용자에게 정확한 상태와 다음 행동을 안내한다.
- 반복 전환과 배터리 부담이 OS 기본 동작보다 크게 늘지 않는다.
- 측정하지 않은 최고 속도·전체 AP 실시간 혼잡도·무중단 연결을 성공 지표로 쓰지 않는다.
