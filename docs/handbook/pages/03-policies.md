# 서비스 정책

인증·권한·수집·오프라인 동작의 기준입니다.

> **확정** 도감은 실제 연결 성공이 기준입니다. 신호 발견이나 연결 시도만으로 해금하지 않습니다.

## 계정과 로그인 수단

### 5.1 로그인 수단별 규칙

| 수단        | 확인하는 것                                                                    | 계정 식별 기준          |
| ----------- | ------------------------------------------------------------------------------ | ----------------------- |
| DataGSM     | OAuth(Authorization Code + PKCE), 활성 재학생 상태. 졸업·자퇴 등 비재학은 거부 | DataGSM 사용자 고유 ID  |
| 학교 이메일 | s로 시작하는 정확한 gsm.hs.kr 주소, 메일로 보낸 일회용 인증번호                | 검증된 이메일 주소      |
| 개인 코드   | 운영자가 발급한 유효한 코드(회수·재발급 버전 확인)                             | 코드가 연결된 내부 계정 |

세 수단 모두 로그인 결과로 와글의 기기 세션을 발급한다. DataGSM 토큰을 와글 API 세션으로 쓰지 않는다. 일반 사용자 인증은 별도 DB의 제한된 /api/client 경로만 사용한다.

### 5.2 계정 연결 (2026-10-31 결정)

사용자가 로그인한 상태에서 다른 수단을 직접 인증해 같은 계정에 연결한다. 아래 세부 규칙은 결정 방향에 따른 기획 제안이다.

- **시작 조건**: 유효한 기기 세션이 있는 상태에서 내 계정 → 로그인 수단 → 추가를 선택한다.
- **새로 인증**: 추가할 수단은 그 자리에서 다시 인증한다(DataGSM 재인증, 이메일 인증번호, 개인 코드 입력). 저장된 정보나 이름·이메일 비교로 대신하지 않는다.
- **수단별 한 개**: 한 계정에는 DataGSM 1개, 이메일 1개, 개인 코드 1개까지 연결한다.
- **아무 계정에도 없는 수단**: 현재 계정에 바로 추가한다.
- **이미 다른 계정에 있는 수단**: 두 계정의 수단을 방금 모두 인증했으므로 "두 계정 합치기" 확인 화면을 보여준다. 사용자가 확인하면 수집 집합을 합집합으로 합치고 현재 계정을 남긴다. 다른 계정의 기기 세션은 회수하고, 그 기기는 다시 로그인하면 합쳐진 계정으로 들어온다. 사용자가 확인하지 않으면 아무것도 바꾸지 않는다.
- **해제**: 마지막 남은 수단은 해제할 수 없다. 해제해도 수집 기록은 계정에 남고 나누지 않는다.
- **관리자**: 계정별 연결 수단과 연결·합치기 시각을 조회하고, 잘못 연결된 수단을 해제할 수 있다. 코드 원문·인증번호·토큰은 기록하지 않는다.
- **자동 병합 금지 유지**: 서버가 이름·이메일·학번을 근거로 먼저 합치거나 합치기를 권하지 않는다.

### 5.3 개인 코드

- 운영자가 한 사람에게 하나 발급하고 대상 구분용 별칭을 붙인다. 원문은 발급할 때만 보여준다.
- 코드만 입력해 로그인한다. 코드를 가진 사람이 로그인할 수 있는 자격증명이므로 전달 경로를 운영 안내에 적는다.
- 회수하면 연결된 기기 세션 갱신이 막힌다. 재발급하면 이전 코드는 쓸 수 없다.
- 선생님이나 DataGSM 재학생 조건에 맞지 않는 이용자는 개인 코드를 사용한다.

### 5.4 운영자

- 사전 지정 운영자 ID 한 개만 관리자 웹에 들어온다. DataGSM ADMIN 역할로 자동 승격하지 않는다.
- 운영자 교체는 서버 운영 설정을 바꾸는 절차로만 한다. 관리자 웹에 운영자 추가·초대 기능은 없다.

## 연결과 수집 규칙

### 6.1 연결 관리

- 현재 연결이 충분하면 유지한다.
- 상태가 계속 나쁘고 더 유리한 후보가 있으면 전환을 시도하거나 OS에 후보를 제공한다.
- 전환 후에는 대기 시간을 두고, 반복 실패한 후보는 잠시 제외한다.
- 모든 후보의 속도를 반복 측정하지 않는다. 신호와 최근 결과로 후보를 좁힌다.
- 자동 관리를 중지하면 앱의 측정·연결 요청을 멈춘다. 현재 OS Wi-Fi 연결은 끊지 않는다.
- 서버 재확인이 실패하면 새 Wi-Fi 요청을 멈추고, 다음 정상 재확인이 끝난 뒤에만 다시 시작한다.

### 6.2 수집

- 해금 조건은 OS가 확인한 실제 연결의 SSID·BSSID·보안 방식이 **공개된 캐릭터가 있는** 등록 AP와 일치하는 것이다.
- 스캔에서 보임, 연결 요청 접수, suggestion 등록 성공, 연결 실패, 시간 초과는 해금이 아니다.
- 같은 계정의 같은 캐릭터는 한 번만 수집된다. 재연결·재시작으로 중복이 생기지 않는다.
- 오프라인에서 확인한 수집은 계정에 묶인 OS 보호 저장소에 보관했다가 서버에 중복 없이 보낸다.
- 서버에는 계정별 "발견한 AP 집합"만 저장한다. 접속 시각·횟수·기기·순서는 저장하지 않는다.
- 서버는 인증된 앱의 보고를 검증하지만, 이것을 무선 접속의 독립적인 증명으로 표현하지 않는다.

### 6.3 캐릭터 공개 조건 (2026-10-31 결정)

- 운영자가 별명과 그림을 모두 등록한 활성 AP만 "공개 캐릭터"다.
- 공개 캐릭터가 아닌 AP는 사용자 도감 목록과 진행률 분모에 나오지 않고, 연결해도 수집되지 않는다.
- 나중에 그림을 등록해 공개하면, 그 뒤 실제 연결을 관찰했을 때 수집된다. 공개 전 연결을 소급해 수집하지 않는다.
- 공개 캐릭터를 비공개로 돌리거나 AP를 비활성화하면 앱 목록에서 사라지지만, 이미 수집한 기록은 보존하고 다시 공개하면 복원한다.
- 현재 구현은 그림이 없는 활성 AP도 "이름 없는 친구"로 앱에 내보낸다. 이 결정에 맞게 서버 도감 API와 앱을 고쳐야 한다(남은 개발 순서 참고).
- 듀얼 밴드 AP처럼 한 장치에 BSSID가 여러 개면 각각 별도 항목이다. 어느 BSSID에 캐릭터를 공개할지는 현장 조사 뒤 운영자가 정한다.

### 6.4 사용자 앱 도감 표시

- 목록: 공개 캐릭터만, 미발견은 회색 실루엣과 가려진 이름, 발견은 컬러 그림과 별명.
- 상세: 그림·별명·소개·수집 상태. 지도·설치 장소·SSID·BSSID 등 기술 정보는 넣지 않는다.
- 캐릭터가 비공개되거나 인증 상태를 잃으면 열린 상세를 닫고 이전 내용을 지운다.

## 운영자와 일반 사용자

학교 이메일·개인 코드·DataGSM의 세 로그인 경로를 제공한다. 관리자는 운영자 한 명이다. 학교 이메일이나 DataGSM의 ADMIN 값만으로 우리 서비스의 관리자 권한을 부여하지 않는다.

개인 코드는 특정 사용자에게 발급하는 로그인 자격증명이다. 같은 사람의 휴대폰·노트북에서 사용할 수 있으며, 전체 값은 발급 시 한 번만 보여준다.

## 최초 설정과 오프라인

첫 설치·로그인·인증·설정 다운로드에는 인터넷이 필요하다. 저장된 설정이 있으면 서버가 잠시 연결되지 않아도 OS와 로컬 설정으로 연결을 지원한다. 새 로그인·코드 검증·변경된 접속정보 수신은 서버 연결 후 처리한다.

## 백그라운드 실행

Windows 창 닫기는 트레이 실행으로 이어지는 구성을 제안한다. Android는 목적에 맞는 실행 방식과 필요한 알림을 사용하고 검색·절전·제조사 정책을 검증한다. 강제 종료·기기 절전 중에도 앱이 항상 실행 중이라고 표시하지 않는다.

## 설치 위치와 개인정보

관리자 지도는 AP의 건물·층·설치 장소를 보여준다. 학생의 GPS·현재 위치·이동 경로를 중앙에 모으는 기능은 첫 버전 범위에 포함하지 않는다.

DataGSM의 고유 사용자 ID와 활성 재학생 상태를 확인한다. 이름·학년·반·번호는 목적이 있을 때 활용한다. 이메일·개인 코드·DataGSM 계정은 이름이나 이메일 일치만으로 자동 병합하지 않는다. 사용자가 로그인 상태에서 다른 수단을 새로 인증해 연결할 수 있다.
