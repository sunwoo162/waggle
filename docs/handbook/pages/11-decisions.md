# 결정 기록과 남은 항목

사용자 결정, 기본 제안, 현장 검증 항목을 구분합니다.

## 사용자와 확정한 사항

| 항목          | 확정 내용                                                          |
| ------------- | ------------------------------------------------------------------ |
| 대상          | 교내 이용자, Android 휴대폰과 Windows 노트북                       |
| 구현 언어     | Android Kotlin, Windows C#                                         |
| 관리자        | 운영자 한 명, 관리자 화면은 웹                                     |
| 네트워크 설정 | 관리자가 정확한 와이파이 이름·비밀번호를 등록                      |
| 학생 이용     | 비밀번호를 직접 입력하는 부담을 없애고 연결 선택을 자동화          |
| 실행 방식     | 초기 설정 후 자동 관리를 켜면 화면 밖에서도 허용되는 범위에서 실행 |
| 학생 로그인   | 학교 이메일 / 개인 초대코드만 입력 / DataGSM                       |
| 학교 이메일   | s로 시작하는 로컬 부분, 정확히 gsm.hs.kr 도메인                    |
| 개인 코드     | 한 사람에게 한 개씩 발급, 본인의 휴대폰과 노트북에서 사용          |
| 도감          | 와이파이마다 재미있는 이름·캐릭터, 미발견은 회색                   |
| 도감 해금     | 실제 와이파이 연결 성공 시 해금. 주변 검색만으로는 해금하지 않음   |
| 관리자 위치   | 등록된 전체 AP의 건물·층·설치 장소 조회                            |
| 디자인        | 사용자 제공 BASE 색·타입·간격·모션 체계                            |
| 작업 방식     | 전체 기획을 먼저 정리하고, 디자인과 제품 개발은 함께 진행          |

## 나머지 기획에 대한 기본 제안

아래는 아직 사용자 확정 요구와 구분되는 제안이다. 전체 기획 검토 때 함께 확인할 수 있게 묶어둔다.

| 항목           | 제안                                                        | 이유                                                                                     |
| -------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 도감 수집 단위 | 관리자가 등록한 도감 항목에 하나 이상의 AP 식별 정보를 연결 | 같은 장치의 여러 주파수·BSSID가 중복 캐릭터가 되는 문제를 피하고 장소별 콘텐츠 구성 가능 |
| 기기 간 도감   | 같은 내부 계정이면 휴대폰·노트북의 수집 진행도 공유         | 두 기기에서 이어서 수집하는 경험 제공                                                    |
| 계정 연결      | 로그인 경로별 외부 ID를 구분하고 자동 병합하지 않음         | 이름·이메일 일치만으로 다른 계정의 도감을 합치지 않음                                    |
| 운영자 인증    | DataGSM 인증 후 사전 지정한 운영자 ID 한 개만 관리자 허용   | 학생 로그인 연동을 활용하면서 관리자 권한은 서비스가 별도로 결정                         |
| 웹·서버        | TypeScript를 주 언어로 제안                                 | 관리자 화면과 API에 같은 언어 사용                                                       |
| 데이터 저장    | 관계형 데이터베이스                                         | 계정·세션·네트워크·AP·캐릭터의 관계와 중복 수집 방지에 사용                              |
| 자동 시작      | 첫 버전은 사용자가 앱에서 시작한 관리 세션을 기준으로 검증  | 부팅 자동 실행·강제 종료 후 재시작은 OS 조건 확인 후 별도 선택                           |
| 품질 검사      | 가벼운 상태 확인, 필요한 경우의 제한된 데이터 전송 검사     | 후보 전부의 속도를 반복 측정하는 부담 감소                                               |

구체 프레임워크·데이터베이스 제품·호스팅·메일 제공업체는 구현 계획에서 정한다. 이 선택을 위해 사용자에게 제품의 세부 동작을 다시 물을 필요는 없다.

## 남은 결정과 현재 위치

사용자 결정이 필요한 제품 제안은 도감 항목 묶음 방식, 같은 계정의 기기 간 도감 공유, 첫 출시의 부팅 자동 시작 범위다. 현재 제안은 관리자가 정한 도감 항목에 AP를 매핑하고, 같은 계정의 진행도를 공유하며, 부팅 자동 시작은 첫 출시의 필수 조건으로 두지 않는 것이다.

학교 SSID 구조·인증 방식·실제 Android 동작은 현장·기기 검증으로 확인할 항목이다. 프레임워크·DB·API 경로·정확한 임계값·알림 구현은 구현 계획에서 정할 항목이다. 이 세 종류를 섞어 같은 수준의 사용자 질문으로 취급하지 않는다.

제품 기획을 바탕으로 구현을 진행하고 있다. 현재 운영자 인증과 네트워크/AP 관리 코드를 작성했으며, 학생 로그인·설정 배포·네이티브 연결·도감은 후속 구현과 현장 검증이 필요하다. 위 미확정 제품 제안은 구현 완료로 간주하지 않는다.

## 상태의 의미

| 상태 | 의미 |
| --- | --- |
| 확정 | 사용자가 선택한 제품 요구 |
| 제안 | 기획 작성자의 기본안, 사용자 확정으로 취급하지 않음 |
| 검증 대기 | 학교·기기·외부 계정에서 확인할 조건 |
| 구현 전 | 문서·설계는 있으나 제품 동작은 아직 만들지 않음 |

문서 기준일은 2026-10-29이다. 이를 모든 결정의 발생일이나 출시일로 사용하지 않는다.
