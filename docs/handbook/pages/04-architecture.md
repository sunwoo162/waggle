# 아키텍처와 데이터

플랫폼의 책임과 서버·기기의 데이터 관계를 정리합니다.


## 구성별 책임

| 구성 | 책임 | 경계 |
| --- | --- | --- |
| 관리자 웹 | 네트워크·AP 위치·캐릭터·코드·사용자 관리 | 운영자 한 명의 인증 필요 |
| 공통 서버 | 인증·권한·설정 배포, 같은 계정의 도감 동기화 | 학교 AP를 직접 제어하는 컨트롤러가 아님 |
| Windows 앱 | 조회·연결 요청·결과 확인·트레이·도감 | 권한·어댑터·드라이버별 동작 확인 |
| Android 앱 | 네트워크 제안·상태 확인·허용된 실행·도감 | 최종 선택은 운영체제가 수행 |
| DataGSM | 기존 학교 계정 인증과 허용된 본인 정보 | 우리 서비스의 관리자 권한과 별개 |

## 정보 흐름

관리자가 등록한 학교 설정은 서버에 저장된다. 로그인한 앱이 설정을 동기화하고, 기기에서 주변 연결을 판단한다. 운영체제의 실제 연결 성공을 관찰하면 수집을 기록한다. DataGSM 로그인 성공과 학교 와이파이 연결 성공은 다른 단계이다.

## 플랫폼별 약속

사용자에게 보여주는 문구는 아래 약속을 넘지 않는다.

| 항목          | Windows                                                 | Android                                                                     |
| ------------- | ------------------------------------------------------- | --------------------------------------------------------------------------- |
| 연결 방식     | Native Wi-Fi로 사용자 프로필 등록, BSSID 선호 연결 요청 | Wi-Fi suggestion 제공. 어느 네트워크에 붙을지는 OS가 결정                   |
| 약한 AP 대응  | 신호·최근 결과로 후보를 비교해 직접 전환                | OS 로밍 우선. 확인되면 더 나은 BSSID로 유도, 아니면 다시 연결 안내          |
| 사용자 문구   | "학교 Wi-Fi를 자동으로 연결하고 관리합니다"             | "비밀번호 없이 학교 Wi-Fi에 붙고, 약한 연결이면 알려드려요"                 |
| 화면 밖 실행  | 트레이 프로세스                                         | 목적에 맞는 서비스 종류와 실행 알림. 절전·제조사 정책으로 멈출 수 있음 안내 |
| 연결 관찰     | OS 연결 상태의 SSID·BSSID·보안 방식                     | NetworkCallback·WifiInfo. 권한이 부족하면 SSID·BSSID가 가려져 수집 불가     |
| 약속하지 않음 | 모든 드라이버에서 같은 전환                             | 강제 전환, 원하는 AP 고정, 무중단 연결                                      |

Android는 위치 권한 없이 SSID·BSSID가 가려질 수 있다. 권한이 부족하면 "도감 수집을 위해 위치 권한이 필요합니다"처럼 이유와 결과를 정확히 보여주고, 가려진 값으로 수집하지 않는다.

### 7.1 Android 실현 방식

공식 문서 근거와 세부 흐름은 [Android Wi-Fi 실현 방식](../../research/2026-10-31-android-wifi-feasibility.md)에 정리했다. 요점:

- **등록**: 활성 네트워크마다 SSID 단위 suggestion을 앱 화면에서 등록하고 OS 승인을 받는다. BSSID는 지정하지 않아 OS 로밍을 막지 않는다. 등록 성공을 연결 성공으로 표시하지 않는다.
- **관찰**: NetworkCallback에 FLAG_INCLUDE_LOCATION_INFO를 붙여 연결된 Wi-Fi의 SSID·BSSID·보안 방식을 받는다. 정밀 위치 권한과 위치 설정이 필요하다. 가려진 값이면 수집하지 않는다.
- **화면 밖**: 관리를 켜면 앱 화면에서 location 유형 포그라운드 서비스를 시작하고 상시 알림을 띄운다. 백그라운드 위치 권한은 요청하지 않는다. 프로세스가 끝나면 앱을 다시 열어야 한다.
- **권한 단계**: 비밀번호 없는 연결은 Wi-Fi 등록 허용만 있으면 된다. 정밀 위치는 약한 AP 비교와 도감 수집에만 쓴다. 위치를 거절해도 연결 기능은 남긴다.
- **실별 SSID의 영향**: OS 로밍은 같은 SSID 안의 AP끼리만 옮긴다. 실마다 SSID가 다르면 학생이 실을 옮겨도 OS는 이전 실 Wi-Fi가 끊길 때까지 붙어 있을 수 있다. 이 경우 같은 앱 suggestion 사이의 OS 재선택(우선순위 조정 포함)이 실제로 일어나는지가 Android 약한 AP 대응의 핵심이며, 첫 실기기 시험 항목이다. 기기별 suggestion 개수 상한(getMaxNumberOfNetworkSuggestionsPerApp)이 실 수보다 큰지도 확인한다.
- **약한 AP 대응**: OS 로밍이 기본이다. 관리 중 현재 신호(RSSI·링크 속도, 위치 권한 불필요)가 일정 시간 나쁘면, OS가 이미 가진 스캔 결과에서 같은 학교 SSID의 더 강한 BSSID를 찾는다. ① 실험: suggestion을 그 BSSID로 잠시 갱신해 옮기도록 유도하고, 옮긴 뒤 BSSID 지정을 풀어 원래대로 돌린다. ② 실기기에서 ①이 안 되거나 위험하면: "더 가까운 학교 Wi-Fi가 있어요" 알림과 Wi-Fi 패널 바로가기만 제공한다. 어느 쪽을 쓸지는 Android 단계 첫 실기기 시험으로 정한다.
- **하지 않음**: 앱의 직접 스캔 요청(백그라운드 30분 1회 제한), BSSID 영구 고정, 사용자 저장 네트워크로 추가(ACTION_WIFI_ADD_NETWORKS는 앱이 이후 수정·삭제할 수 없음).
- **수집 경로 무관**: 학생이 직접 저장한 학교 Wi-Fi로 붙어도 OS가 확인한 연결이 등록 AP와 같으면 수집한다.
- **제안 기준**: 최소 Android 12(API 31), target 36. Android 11 이하는 지원하지 않는다.

## 데이터와 개인정보

### 8.1 서버가 저장하는 것

| 데이터      | 내용                                                 | 보관              |
| ----------- | ---------------------------------------------------- | ----------------- |
| 계정        | 내부 ID, 상태                                        | 계정 삭제 시까지  |
| 로그인 수단 | DataGSM 고유 ID, 검증된 이메일, 개인 코드 다이제스트 | 해제·삭제 시 제거 |
| 기기 세션   | 플랫폼, 발급·갱신·회수 상태                          | 회수·만료 후 정리 |
| 수집 집합   | (계정, AP) 쌍만                                      | 계정 삭제 시까지  |
| 학교 설정   | 네트워크·접속정보(암호화)·AP·위치·도면·캐릭터        | 운영자가 관리     |

DataGSM 응답의 학급·기숙사 등 로그인에 필요 없는 학생 정보는 저장하지 않는다.

### 8.2 기기에만 저장하는 것

- 현재 신호, 최근 검색 결과, 최근 연결 결과·실패 이유.
- 오프라인용 승인된 설정, 서버로 보내지 않은 수집 보고.
- 세션과 학교 접속정보는 OS 보안 저장소(Windows DPAPI, Android Keystore)에 보관한다.

### 8.3 수명주기 (제안)

- **졸업·자퇴**: DataGSM 신규 로그인은 거부한다. 기존 계정은 학년 말에 운영자가 비활성화·삭제할 수 있다.
- **계정 삭제**: 사용자가 내 계정에서 요청하거나 운영자가 실행한다. 로그인 수단·세션·수집 집합을 함께 삭제한다. 백업에 남은 기간은 운영 안내에 적는다.
- **회수의 한계**: 코드·세션 회수는 와글 서비스 접근을 막을 뿐, 이미 OS에 저장된 학교 Wi-Fi 비밀번호를 무효화하지 않는다. 이를 화면에서 과장하지 않는다.

### 8.4 보안 (2026-11-01)

와글 서버에는 학교 모든 실의 Wi-Fi 비밀번호가 모인다. 학생 한 명이 실 하나의 비밀번호를 아는 것보다 **서버·운영자 계정 하나가 뚫리는 것이 훨씬 큰 사고**다. 보호의 중심을 서버와 운영자 계정에 둔다.

| 위협                                 | 영향                                  | 대응                                                                                                                                                           | 상태                                |
| ------------------------------------ | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 운영자 계정 탈취                     | 모든 실 비밀번호 노출·변조            | 사전 지정 운영자 ID만 허용, 짧은 관리자 세션, 비밀번호 열람·변경·코드 발급 전 재인증, 관리자 작업 기록(값 없이 누가·언제·무엇)                                 | ID 제한 구현, 나머지 보강 필요      |
| 서버·DB·백업 유출                    | 비밀번호 대량 노출                    | 접속정보 암호화 저장, 암호화 키를 DB·백업과 분리 보관, 백업도 암호화, 키 교체 절차                                                                             | 암호화 구현, 키 분리·백업 확인 필요 |
| 개인 코드 추측·유출                  | 남의 계정으로 비밀번호 수령           | 충분히 긴 무작위 코드, 로그인 시도 제한, 회수·재발급 버전, 기기 세션 조회·회수                                                                                 | 구현, 현장 전 재점검                |
| 앱 설정 응답 가로채기                | 비밀번호 노출                         | 운영 서버 HTTPS 필수, 앱은 평문 HTTP 거부, 비밀번호를 로그·오류·진단 자료에 남기지 않음                                                                        | 운영 서버 준비 시 확인              |
| 기기에서 비밀번호 꺼내기             | 학생이 다른 실 비밀번호 확인          | 막을 수 없다(Windows 저장 프로필, 루팅 기기). 학생은 지금도 실 비밀번호를 알고 있으므로, 배포하는 네트워크는 "학생이 알아도 되는 것"만 등록한다(2.1 배포 범위) | 운영 규칙                           |
| 가짜 AP(같은 SSID·비밀번호의 핫스팟) | 학생 기기가 가짜 AP에 자동 연결, 감청 | 공유 비밀번호 방식의 근본 한계라 앱으로 막을 수 없다. 와글 API는 HTTPS 인증서 검증으로 보호하고, 학교에 위험을 알린다                                          | 학교에 안내                         |
| 비밀번호 유출 후 대응                | 회수해도 기기에 남음                  | 학교가 해당 실 비밀번호를 바꾸고 운영자가 와글에 반영하면 앱이 다음 동기화 때 재등록. 동기화 주기(앱 열 때 + 관리 중 주기)를 구현 계획에서 정함                | 절차 문서화 필요                    |
| 수정한 앱의 가짜 수집 보고           | 도감 부정 수집                        | 순위·보상이 없으므로 허용하는 위험으로 둔다. 연결 증명으로 쓰지 않는다                                                                                         | 수용                                |
| 기기 분실                            | 세션·비밀번호가 남은 기기             | 내 계정·관리자 화면에서 기기 세션 회수. 기기의 Wi-Fi 저장은 남는다고 안내                                                                                      | 세션 회수 구현                      |

보안 점검은 Windows 현장 시험 전에 한 번, 시범 운영 전에 한 번 별도 단계로 수행한다(남은 개발 순서 참고).

> **확정** 등록 AP마다 캐릭터 하나를 두고 같은 내부 계정의 휴대폰·노트북에서 수집 상태를 공유합니다.

## 관계의 핵심

- 사용자 한 명은 여러 기기 세션을 가질 수 있다.
- 네트워크 하나에 여러 AP를 연결할 수 있다.
- 물리 AP 하나(BSSID 묶음)에 캐릭터 하나를 연결한다.
- 같은 사용자·같은 도감 항목의 첫 해금은 중복 생성하지 않는다.
- 내부 계정 하나에 로그인 수단을 종류별로 하나씩 연결할 수 있다.
- DB 제품·세부 스키마·인덱스·API 경로는 구현 계획에서 정한다.
