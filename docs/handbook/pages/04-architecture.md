# 아키텍처와 데이터

플랫폼의 책임과 서버·기기의 데이터 관계를 정리합니다.


## 구성별 책임

| 구성 | 책임 | 경계 |
| --- | --- | --- |
| 관리자 웹 | 네트워크·AP 위치·캐릭터·코드·사용자 관리 | 운영자 한 명의 인증 필요 |
| 공통 서버 | 인증·권한·설정 배포, 같은 계정의 도감 동기화 | 학교 AP를 직접 제어하는 컨트롤러가 아님 |
| Windows 앱 | 조회·연결 요청·결과 확인·트레이·도감 | 권한·어댑터·드라이버별 동작 확인 |
| Android 앱 | 네트워크 제안·상태 확인·허용된 실행·도감 | 최종 선택은 운영체제가 수행 |
| DataGSM | 기존 학교 계정 인증과 허용된 본인 정보 | 우리 서비스의 관리자 권한과 별개 |

## 정보 흐름

관리자가 등록한 학교 설정은 서버에 저장된다. 로그인한 앱이 설정을 동기화하고, 기기에서 주변 연결을 판단한다. 운영체제의 실제 연결 성공을 관찰하면 수집을 기록한다. DataGSM 로그인 성공과 학교 와이파이 연결 성공은 다른 단계이다.

### 7.1 Android 실현 방식 (2026-11-01 경량화)

- **등록만 한다**: 켜면 활성 네트워크마다 SSID 단위 suggestion을 등록한다(BSSID 미지정). 등록 성공을 연결 성공으로 표시하지 않는다. 설정이 바뀌면 다시 넣어 갱신한다.
- **상주하지 않는다**: 포그라운드 서비스·상시 알림·정밀 위치를 쓰지 않는다. 설정 갱신은 앱을 열 때와 WorkManager 주기 작업(하루 몇 번 수준)으로 한다.
- **OS 동작을 그대로 쓴다**: AOSP 네트워크 선택은 화면이 켜져 있을 때 현재 Wi-Fi가 약하면 다른 SSID 후보 중 점수가 높은 곳으로 옮긴다. 사용자가 직접 저장한 Wi-Fi가 앱 suggestion보다 우선한다. 앞서 검토한 BSSID 유도 실험은 이득이 작고 끊김 위험이 있어 넣지 않는다.
- **끄기·로그아웃**: 와글 suggestion을 모두 제거한다. API 33+는 LINGER로 잠시 뒤 끊는다.
- **도감(선택)**: 도감을 켜는 사용자에게만 정밀 위치를 요청하고, 앱이 열려 있을 때 현재 연결을 확인해 수집한다. 화면 밖 수집은 하지 않는다.
- **위젯·빠른 설정 타일 (2026-11-01 결정)**: 바탕화면 위젯(Jetpack Glance)과 알림창 빠른 설정 타일(TileService)로 켜기·끄기를 제공한다. 둘 다 추가 권한이 없다. **표시는 최소로**: 와글 아이콘과 버튼 하나만 둔다. 꺼져 있으면 흐린 아이콘과 "켜기", 켜져 있으면 채워진 아이콘과 "끄기"로 바뀐다. 개수·시각·실 이름 같은 정보는 넣지 않는다(자세한 상태는 앱에서). **위젯 그림은 와글 캐릭터 (2026-11-01 결정)**: 꺼짐은 자는 얼굴, 켜짐은 깬 얼굴 두 장을 쓴다. 그림이 준비되기 전에는 빈/채워진 Wi-Fi 아이콘으로 대신한다. 위젯은 기능 하나(켜기/끄기), 1×1·2×1 크기, 시스템 모서리 둥글기, 폰 테마 색(Material You)과 다크 모드를 따른다. 빠른 설정 타일은 토글형 타일로 선언하고 아이콘은 24dp 흰색 단색 벡터(꺼짐: 빈 Wi-Fi, 켜짐: 채워진 Wi-Fi), 이름 "와글", 보조 문구 "켜짐/꺼짐", 색은 시스템이 칠한다. 잠금 화면에서 끄기는 잠금 해제 후 실행(unlockAndRun). 처음 켜기(OS 허용 창)는 앱 화면이 필요하므로 그 전에 누르면 앱을 연다. Android 13+는 앱 안에서 타일 추가를 제안한다. 상시 알림은 쓰지 않는다.
- **확인 필요**: 기기별 suggestion 개수 상한과 실 수, 첫 허용 창 흐름, 학생이 이미 저장한 실 Wi-Fi와의 관계.
- **기준**: 최소 Android 12(API 31), target 36.

## 데이터와 개인정보

### 8.1 서버가 저장하는 것

| 데이터      | 내용                                                 | 보관              |
| ----------- | ---------------------------------------------------- | ----------------- |
| 계정        | 내부 ID, 상태                                        | 계정 삭제 시까지  |
| 로그인 수단 | DataGSM 고유 ID, 검증된 이메일, 개인 코드 다이제스트 | 해제·삭제 시 제거 |
| 기기 세션   | 플랫폼, 발급·갱신·회수 상태                          | 회수·만료 후 정리 |
| 수집 집합   | (계정, AP) 쌍만                                      | 계정 삭제 시까지  |
| 학교 설정   | 네트워크·접속정보(암호화)·AP·위치·도면·캐릭터        | 운영자가 관리     |

DataGSM 응답의 학급·기숙사 등 로그인에 필요 없는 학생 정보는 저장하지 않는다.

### 8.2 기기에만 저장하는 것

- 현재 신호, 최근 검색 결과, 최근 연결 결과·실패 이유.
- 오프라인용 승인된 설정, 서버로 보내지 않은 수집 보고.
- 세션과 학교 접속정보는 OS 보안 저장소(Windows DPAPI, Android Keystore)에 보관한다.

### 8.3 수명주기 (제안)

- **졸업·자퇴**: DataGSM 신규 로그인은 거부한다. 기존 계정은 학년 말에 운영자가 비활성화·삭제할 수 있다.
- **계정 삭제 (2026-11-01 구현)**: 학생이 Windows·Android 앱의 "계정 삭제"로, 또는 운영자가 개인 코드 화면의 "삭제"로 실행한다(운영자는 최근 로그인 필요, 작업 기록에 남음). 개인 코드·모든 기기 세션·수집 집합·내부 사용자를 함께 지우고 되돌릴 수 없다. 앱은 삭제 뒤 로그아웃과 같은 로컬 정리(와글 Wi-Fi 등록 삭제 포함)를 한다. 백업에 남은 기간은 운영 안내에 적는다.
- **비재학 계정 정리 절차**: 학년 말에 운영자가 졸업·전학 대상 개인 코드를 확인하고 개인 코드 화면에서 삭제한다. 등록 요청에는 요청자 정보가 없어 따로 지울 것이 없다.
- **회수의 한계**: 코드·세션 회수는 와글 서비스 접근을 막을 뿐, 이미 OS에 저장된 학교 Wi-Fi 비밀번호를 무효화하지 않는다. 이를 화면에서 과장하지 않는다.

### 8.4 보안 (2026-11-01)

와글 서버에는 학교 모든 실의 Wi-Fi 비밀번호가 모인다. 학생 한 명이 실 하나의 비밀번호를 아는 것보다 **서버·운영자 계정 하나가 뚫리는 것이 훨씬 큰 사고**다. 보호의 중심을 서버와 운영자 계정에 둔다.

| 위협                                       | 영향                                  | 대응                                                                                                                                                                                                         | 상태                                          |
| ------------------------------------------ | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| 운영자 계정 탈취                           | 모든 실 비밀번호 노출·변조            | 사전 지정 운영자 ID만 허용, 관리자 세션 8시간, 네트워크(비밀번호)·개인 코드·등록 요청 처리는 최근 15분 안의 로그인 필요, 관리자 작업 기록(값 없이 누가·언제·무엇), 관리자 화면 프레임 삽입 금지 등 보안 헤더 | 구현(2026-11-01)                              |
| 서버·DB·백업 유출                          | 비밀번호 대량 노출                    | 접속정보 암호화 저장, 키 교체 명령(`npm run settings:rotate-key`), 암호화 키를 DB·백업과 다른 곳에 보관(운영 절차)                                                                                           | 암호화·키 교체 구현, 키 분리 보관은 운영 단계 |

보안 점검은 Windows 현장 시험 전에 한 번, 시범 운영 전에 한 번 별도 단계로 수행한다(남은 개발 순서 참고).

> **확정** 등록 AP마다 캐릭터 하나를 두고 같은 내부 계정의 휴대폰·노트북에서 수집 상태를 공유합니다.

## 관계의 핵심

- 사용자 한 명은 여러 기기 세션을 가질 수 있다.
- 네트워크 하나에 여러 AP를 연결할 수 있다.
- 물리 AP 하나(BSSID 묶음)에 캐릭터 하나를 연결한다.
- 같은 사용자·같은 도감 항목의 첫 해금은 중복 생성하지 않는다.
- 내부 계정 하나에 로그인 수단을 종류별로 하나씩 연결할 수 있다.
- DB 제품·세부 스키마·인덱스·API 경로는 구현 계획에서 정한다.
